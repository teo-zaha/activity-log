# Secure secrets: sealed values in `config.toml`, one key in the OS store

Tokens and secret links (`GITLAB_TOKEN`, `JIRA_TOKEN`, `CALENDAR_ICS_URL`) are no longer kept in `config.toml` as plain text. Each one stays in its table, but sealed: `token = { sealed = "v1:os:<kid>:<btag>:<base64url>" }`. One random 512-bit key, the only thing in the OS secure store, opens them all. This is the pattern of Chrome's "Safe Storage" and Electron's `safeStorage`.

## Why sealed values and one key

We weighed one store item per secret, one store item holding a map of every secret, and sealed values in the file with one key in the store. We chose the last for these reasons:

- **One atomic write.** A secret and the table that names it are published by the same owner-only rename (`platform/private_file`), so a crash leaves the old file or the new one. The two other designs write two stores with no transaction between them and must sweep orphans.
- **What compares stored text keeps working.** Sealing is deterministic (AES-SIV), so `EditBase`/`Precondition`, `ConfigFile::set`'s no-op check, the collection key and `affected_kinds` need no marker generations. A token entered again unchanged, for the same server and setting, seals to the same text. Every other case (another key, another binding, the first seal of plain text) reads as a change, which is the safe direction: a conflict or a check run again, never a missed change.
- **No dependency on `instance`.** Renaming a connection keeps its secret, removing the table removes it, and a table pasted in `config edit` keeps its token.
- **One prompt.** On macOS each program sees one Keychain dialog per update, not one per token. The key is 64 bytes, far under Windows' 2,560-byte credential limit.
- **The key file uses the same format** where no OS store exists.

What we accept: we own a small format (built only from RFC 5297 and RustCrypto, no nonce or padding of our own); losing the key loses every secret at once, and the checks then say to enter them again; a sealed value reveals its length, and that two connections hold the same token under the same binding; the Keychain shows one opaque item, not each token.

## What it protects

A copy of `config.toml` (a backup, a dotfiles repository, a paste into an issue, a synced folder) leaks no token, nothing logs or sends a secret, and the dashboard never receives one. On macOS a program not on the key's access list cannot read it without a dialog naming that program. It does not stop malware the user approves in that dialog (unsigned builds show it after every update, which trains people to allow it), malware that patches a binary the user owns, malware that reads a running process's memory, or malware that drives our own CLI. On Windows and Linux, DPAPI and an unlocked Secret Service give the key to any process of the user without a prompt; there the gain is only that copies of the file are useless. None of this is weaker than plain text, and all of it is stronger for copies.

## The format

- Only an inline table with exactly the key `sealed` is sealed. A string is always plain text, and any other shape is refused with a warning. Nothing sniffs prefixes.
- The text is `v1:<store>:<kid>:<btag>:<base64url(SIV tag ‖ ciphertext)>`, read strictly, so each value has one form: `store` is `os` or `file`, the store that holds the key; `kid` is the first 8 lowercase hex digits of SHA-256(`"activity-log/v1 key id"` ‖ key); `btag` is the first 8 lowercase hex digits of SHA-256(`"activity-log/v1 binding"` ‖ the number of binding components ‖ each component, every count and length a big-endian `u64`); the payload is canonical base64url without padding, at least the 16-byte synthetic IV long. An empty secret is never sealed, nor any field `is_secret()` does not name. Five vectors (GitLab with the OS store, also on an IPv6 address and another port; Jira on another port, `insecure`, with the key file, also with an IDNA host, a spelled `insecure` and a Unicode secret; Calendar, with no binding) are pinned in the tests, each computed or opened independently from these definitions with pyca/cryptography's AES-SIV over OpenSSL, and RFC 5297's A.1 and A.2 vectors check the crate's multi-header API.
- The cipher is `Aes256Siv` (`aes-siv`) through its multi-header API, so S2V authenticates each part of the associated data separately and no concatenation is ambiguous. The associated data is, in order: `activity-log/v1`; the header `v1:<store>:<kid>:<btag>`; the wire key name (`GITLAB_TOKEN`), so a value moved to another field does not open; one `<WIRE_NAME>=<normalized value>` per binding key of the kind, in declaration order.
- Opening decides before it decrypts: a `kid` the process has no key for is `OtherKey`; otherwise a `btag` other than the one computed from the file's binding values is `OtherAddress`; otherwise a failed open is `Damaged`. `btag` hashes values that are in the file in clear, and it is authenticated as part of the header, so editing it only turns `OtherAddress` into `Damaged`.

## Binding a token to its server

A GitLab or Jira token opens only for the server origin it was entered for, and a Jira token only with the same `insecure` setting. A file edit that points a token elsewhere leaves it unopened, so it is never sent there; a save through the app or the CLI that changes the binding must bring the token again (the issue sits at the token field), and the CLI prompts for it. The binding keys are declared once, with a `[binds]` mark in `provider_config!`: `GITLAB_URL`, `JIRA_URL` and `JIRA_INSECURE`. Calendar has none: its secret is its own address. A URL binds by its origin as `url` parses it (scheme and host lowercased, IDNA as ASCII, the port always explicit, `https://gitlab.example.com:443`), and only an `http` or `https` address without a user name or password has one, the rules the remote client sends a token by; a bool as `parse_bool` reads it, unset meaning `false`. A binding belongs to its kind: sealing or opening another kind's field with it is refused before anything is decrypted. The binding tag is only a hint for display (the settings' "saved for another server"): 4 bytes can be matched by about 2³² tries, so the save path compares bindings, never tags, and opening authenticates the binding's values themselves.

`ProviderConfigValueType::Password` stays the one marker of a secret, read only through `ProviderConfigKey::is_secret()`: redaction in `Debug`, the fingerprint, the settings snapshot, the CLI's hidden prompt, sealing, opening and the import. `ProviderConfigKey::binds` is the other declared fact, read only by sealing and by the save path's binding check.

## Where the key lives

`platform/secret_store` holds exactly one item, one OS child per platform under the `imp` alias:

- macOS: a generic password with service `Activity Log` and account `config key` (`security-framework`), created in the default keychain (the login keychain unless the user changed it) and read through the keychain search list, so a changed default does not make it look absent. Every keychain call of a process runs under one lock, since a read without dialogs turns them off for the whole process;
- Windows: the generic credential `activity-log/config-key`, persisted `CRED_PERSIST_LOCAL_MACHINE`, so a roaming profile does not carry the key to a server (`windows`, `Win32_Security_Credentials`);
- Linux: the Secret Service's default collection, attributes `application=activity-log` and `purpose=config-key`, through `oo7`'s D-Bus backend directly (its default would pick the Flatpak portal in a sandbox), each call bounded at 5 s.

We use the OS APIs directly rather than `keyring`: `keyring` 3 silently uses a mock store without features and 4 removed its native-store features, and neither it nor `keyring-core` gives a definite absence or a no-prompt mode more easily.

A store answers `Found(key)`, `Absent` or a `StoreError` of kind `Unavailable` (no such store here: no default keychain, `ERROR_NO_SUCH_LOGON_SESSION`, no session bus or Secret Service), `Refused` (it exists but would not give the key now: interaction not allowed over SSH, a cancelled dialog, a dismissed unlock prompt) or `Failed`. `Absent` is definite: the store answered, is usable, and has no such item. A locked collection is not absent, nor is an empty search of a collection still locked once it answered (KeePassXC answers every search of a locked collection empty); only a missing bus or Secret Service, found while connecting, is `Unavailable`, and any other failure there `Failed`. An item that holds anything but a key's 64 bytes is `Failed`, and no key is ever created over anything but `Absent`. The keychain refuses to add an item that exists; Credential Manager would replace one and the Secret Service would add a second, so both are looked for again, under the key-creation lock, just before one is created.

The key file, where it is used, is `secret.key` in a local, non-roaming folder (`%LOCALAPPDATA%\activity-log`, `~/Library/Application Support/activity-log`, `${XDG_DATA_HOME:-~/.local/share}/activity-log`), written owner-only through `platform/private_file` (`Folder::replace`) and refused where that folder cannot be kept private: a header line naming the format, then the key in hex. A key file is used only if it is a regular file the user owns that no other account may read or write (no group or other mode bits and no extended ACL entry on macOS and Linux, no rights for another account on Windows), judged on the handle it is read through, in a folder no other account can change. `ACTIVITY_LOG_SECRET_KEY_FILE` overrides its path, for a Docker volume and for tests of built binaries. It follows the same absence and create-if-absent rules; a key file that holds no key is `Failed` and stays as it is.

## Stores per front end

- **The desktop app seals only with the OS store.** Without one a save is refused as `secretStoreUnavailable`, and when the store refuses as `secretStoreRefused`, with the draft kept. It opens values sealed with the key file too, which the CLI may have written, so one shared `config.toml` works in both; it only ever reads the key file and never creates it (the dev profile aside, below).
- **The CLI seals with the OS store, and falls back to the key file only when the OS store is `Unavailable`**, with one warning per process that `sources` and every edit print. A `Refused` store is never a reason to fall back: the edit fails as `secretStoreRefused`, with the hint to run in the desktop session or to set `ACTIVITY_LOG_SECRET_STORE=file`.
- **The API server never writes the config, so it never seals.** It opens each value from the store that value names, and reports which store new secrets would use by the CLI's rule.
- **`ACTIVITY_LOG_SECRET_STORE`** chooses where the key lives and configures no source: `os` forbids the CLI's fallback, `file` forces the key file in the CLI and the API (a Mac over SSH, a CI runner where a prompt would hang). The desktop app ignores it outside the dev profile and logs that it did.
- **The settings show the choice** as `ProvidersResponse.secretStore`, a `SecretStoreInfo` union with one state each for: the OS store in use; the OS store found but refusing at the probe (saves would be `secretStoreRefused` until it answers); the key file in use, because there is no OS store, because it was forced, or because of the dev profile; and no store at all (the desktop without an OS store). It comes from a cheap probe that never prompts, at start and again after a store error. Each secret field in the snapshot shows how it is stored, read from the file alone: sealed with its store, sealed for another server or TLS setting (its `btag` does not match the table's binding, so the settings never say "Stored securely" next to that problem), plain text, or not set.

## Reading

`ConfigFile::connections()` stays free of the store: a secret field holds a `StoredSecret`, `Plain` or `Sealed`, compared by its stored form, and the snapshot, `sources` without checks, `config path` and label edits never touch the store. A connection's values are opened once per check, when `ProviderRuntime` resolves its config, before `STARTUP_CHECK_TIMEOUT` starts, so waiting for a dialog never counts as a slow server. Meanwhile the connection is `checking` with the reason "Waiting for the keychain", bounded by `KEY_WAIT` (120 s). `Secrets`, the per-process handle, holds the store choice and the key once read; concurrent first requests share one attempt, so one dialog appears, and a refusal is not kept. A collection uses only the key already held and never prompts.

An opened value reaches the provider in a `Zeroizing<String>`; zeroizing is best effort, since the token is copied into request headers and TLS buffers we do not own. `OtherKey` and a missing key make the connection `notConfigured` ("This token was saved on another computer, or before this computer's keychain was reset. Enter it again."), `OtherAddress` too ("… saved for another server or TLS setting"), and so does `Damaged`. A `StoreError` is the new problem `secretUnavailable`, which can be checked again; `problem_of` maps it, also when a collection meets one, so it is never `timedOut` or `collectionFailed`. The CLI's `problem_terms` counts it as configured but not working, failing the run.

## Writing

Every writer still goes through `settings::edit_config` or `edit_externally`. A writer that brings a new secret first obtains a `Sealer` from its `Secrets` (`Secrets::sealer`, the store its front end seals with, the key read fresh) and hands it to `edit_config`; every other writer hands none, and nothing is sealed. `config edit` asks for one through a callback, only once the edited copy holds a new plain-text secret:

1. Only when the request carries a new secret value, and before the config lock (a dialog can take as long as the user takes), the writer reads the key from the store again, with the interaction it allows (allowed for a save, never at desktop start), creation included; the per-process key is for readers only, so a key another process deleted or replaced is noticed before anything is sealed with it. On a definite `Absent` it takes the key-creation lock (`secret-key.lock` in the OS config folder, else beside the config, so every config on the computer shares one; `secret.key.lock` beside the key file for the key file's key; a lock another process holds past the settings writer's 5 s wait is `Refused`), reads once more, and, if the file holds values of that store (`os`, or `file` when the key being created is the key file's) whose `kid` matches no key, logs one warning naming their count: they must be entered again here. It then generates 64 random bytes, stores them only if still absent, reads them back through a fresh lookup and compares the bytes with what it generated.
2. Under the config lock the change seals its new values, refuses a binding change without a new token (`BindingChanged`), and refuses a new secret whose table names nothing to bind it to, such as a token before its URL (`SecretUnbound`, `invalidRequest`): the app never writes a secret it brought as plain text. Before publishing, it parses the bytes about to be published and opens every sealed value in them that is stored otherwise than in the file as read under the lock, with the binding computed from that output document. A value that does not open fails the edit as `internal`, and nothing is written. A value the edit left as it was is not opened: one sealed for an address edited since by hand stays as it was and blocks no other save.
3. The owner-only publish, as before.

The values checked before publishing are those the writer's key sealed (its store and key id): a value another key sealed is not the writer's to open, and is as the file had it. The binding guard compares `Binding` values, never tags, for every connection whose sealed secret the edit left as it was; the settings' check of a draft (`check_save`) applies the draft to a copy of the file and reports the same refusal at the secret's field, and the CLI's `sources set` of a binding key asks for the token in a terminal; outside one it refuses unless the token comes in the same call (`--secret -` reads it from standard input). `-` with nothing on standard input (it ended, or brought an empty line) fails and changes nothing; only `sources unset` clears a value. `config edit` saves a new address under a sealed token as written, with one warning per connection whose token must be entered again. A secret given to the CLI as an argument is warned about, since other programs can see a command line; `-` reads it from standard input.

Plain text already in the file, hand-written or from unreleased builds, is still read, and it is sealed only opportunistically: in an edit that already read the key for a new secret, at desktop start before the host first loads (never prompting: Windows, an unlocked Linux collection, or macOS with interaction disabled while nothing else runs; the key lookup waits at most 5 s, then the pass is skipped for this start with one line in the log), and in `config edit` when the user typed a new plain-text secret. Sealing it never fails an edit and never prompts; one whose table names nothing to bind it to stays plain text, with a warning. An unrelated edit (a label, a list, a removal) never reads the store. When `config edit` meets a new plain-text secret and the store refuses or is missing, the edit publishes that plain text with a warning; it never fails. Sealing marks no table touched, so it backfills no `instance`.

## Dev profile

`ACTIVITY_LOG_PROFILE=dev`, which `api:start`, `api:dev`, `cli:collect` and `desktop:dev` set, gives a development build its own config (`<config dir>/activity-log-dev/config.toml`), cache and key file, and always the key file: the keychain is never touched, so rebuilds never prompt and developers never seal into their real keychain. `--config` and `ACTIVITY_LOG_CONFIG` still choose the config path; the store stays the key file. It is honoured only under `cfg(debug_assertions)`: a release build (the installed app and CLI) ignores the variable and logs one line, so a stray value can never stop it from starting. An unknown value in a debug build is refused at start. A build that uses it says so once at start, and the desktop's window title carries "(dev)". The test scripts do not set it: tests build their own `Secrets` and, for built binaries, point `ACTIVITY_LOG_SECRET_STORE=file`, `ACTIVITY_LOG_SECRET_KEY_FILE` and `ACTIVITY_LOG_CONFIG` at temporary paths. Since `pnpm cli:*` runs with the dev profile, the README shows the installed `activity-log` binary for real use and `pnpm cli:*` for development only.

## Importing 0.0.7's sources once

Activity Log 0.0.7 had no `config.toml`: the desktop kept a Tauri Store `settings.json`, and the CLI and the API read a `.env`. A user upgrading from it would start with no sources, so the first start imports them once, and only when the config path is the default one (no `--config`, `ACTIVITY_LOG_CONFIG` or dev profile), no `config.toml` exists there (an empty one counts, so removing every source never brings them back), no marker exists, and a legacy file is found.

- The reader is 0.0.7's own, ported (`read_store_provider_config`, `ProviderConfig`'s `list` and `bool`, `parse_config_list`, `parse_bool`, `parse_wsl_repo`), with two rules of the import's own: a blank value is unset, and the process environment is never read. The tests' expected values are computed through it. A `settings.json` 0.0.7 would have refused (another type, a list with an item that is no string, not JSON) imports nothing and says why, without a marker, so a repaired file imports later. Every value then goes through `settings::view::normalize`; one it refuses is left out and reported (`invalid`), never written. Tokens are sealed and bound as any other; a token whose connection has no address to bind it to is left out (`noAddress`), never written as plain text. A `WSL_GIT_DIRS` item that is no `Distro:/path` is counted (`invalidWslRepo`).
- The mapping: a GitLab and a Jira connection where any of their keys is set (`insecure = true` only when 0.0.7 read it as true), the local Git connection 0.0.7 always ran (`GIT_DIRS` unset is the home default, none is `dirs = []`), on Windows one WSL Git connection per distribution searched (the registry's while `WSL_DISTROS` is unset) or holding `WSL_GIT_DIRS` repositories (a searched one with repositories searches `~` too), and Outlook and System where today's adapters run. Each connection gets its kind's default label. Unknown keys are logged by name.
- The desktop looks for `settings.json`; the CLI for `settings.json` and for a `.env`, found as 0.0.7 found it (the first regular file walking up from the working directory) by our own finder, which skips a file another account owns (the file is opened once, a link followed, its owner judged on that handle and its bytes read through it; on Windows the owner SID must be the user's), and parsed by `dotenvy::from_read_iter`, which touches no environment. A `.env` that sets none of 0.0.7's keys (a project's own, with a database address) is no settings file of 0.0.7's: it counts as not found, and nothing is written. The first of a repeated key wins, as 0.0.7's `dotenv()` never replaced a variable it had set, and a line that does not parse ends the file there, as it ended 0.0.7's load; the warning says a line stopped it, never its text. That parser fills `$VAR` and `${VAR}` in from the process environment, as 0.0.7's did, which a `.env` from anywhere (a cloned project's) could use to send one of the environment's secrets to a server it names. So a setting whose line holds a `$` outside single quotes and not escaped is left out and reported (`readsEnvironment`), whatever it came to; a `$` in a trailing comment counts too. A left-out WSL key searches nothing rather than the registry's guess. The process environment is never imported.
- When the CLI finds both, `settings.json` wins only if its `providerConfig` sets at least one key 0.0.7 read, as the import's own rules read it (Q12: not `null`, not blank); otherwise a `.env` that reads is used, then a `settings.json` that sets nothing (0.0.7 still ran Git and the local sources from it). The report names the file used and the one found but not used.
- A secret needs the key first. The desktop's start asks the store without a dialog (creation included), so a store that needs one (a locked keychain, a key another build made) shows none at every start: the import waits (`postponed`, `refused`) and the notice's Import (`import_legacy_settings`) asks again with dialogs allowed, the user having chosen it; a missing store waits too, the notice opening the settings. The desktop writes tokens only into the OS store. The CLI asks with dialogs allowed, falls back to the key file when the store is unavailable, and imports nothing when it refuses.
- An import that is due and not done (waiting for the store, a file that does not read, a write that failed: a busy lock, a location that keeps no file private, a sealed value that does not check, each reported as `failed` with its reason) is given up by the first `config.toml` any writer makes. The CLI therefore refuses a command that writes the settings while it waits, saying why and how to go on: run any command again once the keychain can answer or the file is fixed, or `activity-log config skip-import`, which writes a marker that gives it up (`given_up = true`). Commands that only read run. The desktop's notice says that adding a source gives the import up.
- The tables are added by `edit_config` with a `Precondition::FileAbsent`, so a process that wrote the file first wins and the import is dropped, and a marker, `legacy-import.toml` beside the config, records what was imported and skipped (`release`, `at`, `used`, `path`, `found_unused`, `imported`, `skipped` by connection, field and reason, never a value) once `config.toml` is published, owner-only and under the same lock. A marker that does not read counts as present and is logged. A failure to write it leaves the import standing: `config.toml` alone stops a second run. The legacy files are only read, never written, moved or deleted.
- The desktop imports, then seals, then builds its host; the CLI imports before every command but `config path`. The API server never imports; finding a legacy file and no config, it logs that `activity-log sources` imports it once.
- What it did is a `LegacyImportReportDto`: `imported` (the file, the one not used, the connections, what was left out), `postponed` (a token and no store: `unavailable` or `refused`), `unreadable` or `failed`, each with its `message` for people. It is logged; the CLI prints the line naming what it imported; the desktop holds it for the dashboard's one `take_legacy_import_report`, which shows a notice: news, not a failure, for values left out (Open Settings at the first source one was left out of, else the Logs), a failure with Import for an import refused or failed, with Open Settings at the settings' home for a missing store, with Dismiss for a file that does not read; nothing for a clean import.

## Contract

- `BackendErrorKind` gains `secretStoreUnavailable` and `secretStoreRefused`, mapped in `core/src/backend_error/` from the edit's typed store error. The API answers both with `503` (it never seals, so it never meets them). The dashboard's stream treats neither as a reason to connect again (they only come from saves), and the settings keep the draft for both, offering Save again for a refusal and the way to set up a keyring for a missing store. A store's `Failed` (a fault of its own: no random bytes, a key that does not read back as stored, a call that stopped) is `secretStoreRefused` on purpose: the settings do the same for it as for a refusal, keep the draft and offer Save again, so a third kind would change nothing on screen; the message tells them apart for people.
- `ProviderProblem` gains `secretUnavailable`.
- A secret field's DTO is the shape `secret` (`valueType`, `stored`), in place of `single` with `secret: true`: `stored` is `null` when unset, else one of `sealed`, `sealedForOtherServer`, `sealedWithOtherKey` (each with its `store`, `os` or `file`), `savedByNewerVersion`, `unreadable` or `plainText`. It is read from the file and from the key `Secrets` already holds, never from a store: with no key held yet it never says `sealedWithOtherKey`, and `sealedForOtherServer` comes from the binding tag, a hint only.
- `ProvidersResponse.secretStore` is the `SecretStoreInfo` union: `{ store: 'os', state: 'ready' | 'refused' }`, `{ store: 'file', why: 'noOsStore' | 'forced' | 'devProfile' }`, `{ store: 'unavailable', why: 'noOsStore' }`. A store that failed its probe shows as `refused`. The host probes once at start, through its spawner and off the state lock, and each recorded check refreshes it, so a store error a check met shows with that check.
- A sealed text that does not read is its own case, never `Damaged`: one of another format version says it was saved by a newer Activity Log, without urging to enter it again; any other is unreadable. Both make the connection `notConfigured`.
- `Host::start` and the desktop's `AppState::start` take a `Secrets` handle. Only the binaries' `lib.rs`/`main.rs` build one over the user's stores, through `Secrets::desktop`, `::cli` and `::api`, which core's own tests cannot reach (`cfg(not(test))`). Core's `test-support` feature exports a scriptable `MemoryStore`, `Secrets::with_stores` and `Secrets::none` for the other crates' tests, and the API, CLI and desktop crates turn it on as a dev-dependency. With it, the front ends' own constructors build no OS store at all, and the key file is only where `ACTIVITY_LOG_SECRET_KEY_FILE` puts it: since `cargo test --workspace` unifies features, that covers the binaries the CLI's tests run too, and no test reaches a keychain or a real key file. Installed builds (`cargo build`, `cargo install`, `tauri build`) never have the feature.
- The tests against a real store are a test binary of their own behind the `real-store-tests` feature, on an item of their own, never the config key: on macOS only in the keychain file `ACTIVITY_LOG_TEST_KEYCHAIN` names (never the login keychain), on Windows and Linux only on a CI runner (`CI=true` and `ACTIVITY_LOG_REAL_STORE_TESTS=1`). Anywhere else the store refuses to be built and the tests fail saying why. CI runs them on all three systems, on Linux also without a session bus, which must be `Unavailable`.

## Known limits

- Each computer has its own key, so a `config.toml` synced between computers is not supported for secrets: a token entered on one replaces the value the other could open. The README says not to sync it.
- `aes-siv` 0.8 (RustCrypto, pinned exactly) has never had a security audit of its own; it builds on RustCrypto's `aes`, `cmac` and `ctr`, and its tests run the RFC 5297 and Wycheproof vectors. Our pinned vectors agree with OpenSSL's AES-SIV.
- On macOS the key file's folder, `~/Library/Application Support/activity-log`, is the one `config.toml` is in, so a copy of that folder carries both the sealed values and the key that opens them. The key file is for where no OS store can be used; the OS store is the one to use.
- Each Secret Service call is bounded at 5 s, a dialog it shows meanwhile (a confirmation some keyrings ask for a new item) included, except an unlock prompt, which waits for the user.
- Zeroizing is best effort: the key lives in one heap buffer wiped on drop; the AES key schedules, the CMAC and the CTR state are wiped when the cipher is dropped (`aes`, `cmac` and `ctr` with their `zeroize` features, unified by core's own dependencies on them); a secret being sealed or opened sits only in buffers wiped on every path; Credential Manager's copy is wiped before it is freed. Out of reach: the keychain's own copy (`security-framework` lends it read-only), the Secret Service's D-Bus buffers, and the stack copies the compiler makes when it moves a value.
- A writer's key is read before the config lock, so it can be stale by the time the file is written: if another process removed the key from the store and created a new one in between, the writer seals with the old key, and the values it wrote show as saved on another computer (`OtherKey`) until they are entered again. Keys are created only over a definite absence, so this needs the store's item deleted by hand meanwhile.
- Sealing is deterministic, so a token entered again unchanged, for the same server and setting, gives the same text: two backups of `config.toml` show whether a token was replaced in between, though not what it is.
- On Windows a `.env` whose owner is the Administrators group (a file an elevated program wrote, on a system that makes administrators' files theirs) counts as another account's: it stops the walk and is not imported. Its settings can be entered again or the file's owner changed.
- The macOS dialog's text, and whether an ad-hoc signed app stays on the access list across an update, are checked by hand before a release. A Developer ID signature would make "Always Allow" survive updates.
