# Route new Outlook calendars through Microsoft Graph

A third-party Windows app has no supported way to read the calendar of new Outlook (olk.exe) from the local machine. New Outlook has no COM, MAPI or VBA object model and no local API, so every reliable path goes through the server. For an Exchange Online mailbox in November 2026, that leaves **Microsoft Graph `GET /me/calendarView`** with delegated OAuth as the one option that has a future. The hard part is not code but consent. Since the November 2025 wave, Microsoft's managed default consent policy, which is the default for new tenants, **blocks users from consenting to any `Calendars.*` permission themselves**, so an Entra admin in the company tenant must grant consent once. After that, colleagues sign in in the system browser and never see a consent prompt again. For this app, register a **single-tenant public client** in the company tenant and request only `Calendars.ReadBasic` and `offline_access`. Sign in with **authorization code + PKCE on a loopback redirect**, run from Rust `core` so the CLI and the desktop app share it, and keep the rotating refresh token in the OS credential store. Expose calendarView as a new API-cached provider, alongside the existing COM collector. A user-published ICS link is the only fallback that needs no admin, and its fidelity is capped by tenant policy. Classic Outlook stays a fully usable path through the existing COM collector, including for this user, and it is supported until at least 2029. The app crash seen while classic Outlook runs is an Activity Log bug, not a limit of the COM route. Graph is the answer for anyone who runs new Outlook, and the only one that survives Microsoft's eventual removal of the switch back to classic.

## New Outlook leaves no local door open

New Outlook is Outlook on the web running inside WebView2. COM and VSTO add-ins are unsupported "for reliability reasons", and Office.js web add-ins are the only extension model ([Microsoft Learn](https://learn.microsoft.com/en-us/office/dev/add-ins/outlook/one-outlook)). VBA is also unsupported ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365-apps/outlook/get-started/state-of-com-add-ins)). As of November 2026, Microsoft has announced no local API, CLI or automation interface to replace them. The repo's Windows collector already recognises this case (`OutlookFallback::NewOutlookOnly` in `core/src/collect/outlook/mod.rs`). Its current message tells users to switch to classic Outlook. That advice remains valid, but once a Graph source exists the message should offer the Graph source as well.

Every local workaround fails on reliability or policy. Microsoft documents that new Outlook keeps "user and app data" in a Chromium IndexedDB store under `%LOCALAPPDATA%\Microsoft\Olk\EBWebView\Default\IndexedDB` ([Microsoft Learn: VDI deployment](https://learn.microsoft.com/en-us/microsoft-365-apps/outlook/get-started/virtualized-desktop-infrastructure)). That store does contain events and calendars. The best public attempt to read it, the m365crawl project in October 2026, could decode the LevelDB files. It found the source **unstable while olk.exe was running** and produced **69,996 unmapped event records** on one import, so it deferred calendar support ([GitHub m365crawl #145](https://github.com/ourostack/m365crawl/issues/145)). The schema is internal to OWA and can change with any weekly build. Recurring events are not even supported offline ([MC1101906](https://mc.merill.net/message/MC1101906)), and a process that reads another app's browser profile looks like credential theft to endpoint security tools.

The WinRT `AppointmentStore` route also fails. It was fed by the Windows Mail and Calendar apps, which reached end of support on 31 December 2024 and no longer sync ([Microsoft Support](https://support.microsoft.com/en-us/help/17198)). There is no evidence that new Outlook writes to it.

An Office.js add-in bridge does not escape Graph either. The Mailbox API exposes only the item the user is looking at, not a date range. Legacy Exchange callback tokens are **turned off across all Microsoft 365 tenants**, which takes `makeEwsRequestAsync`-style access with them. Microsoft's replacement is nested app authentication to Graph ([Microsoft Learn: NAA FAQ](https://learn.microsoft.com/en-us/office/dev/add-ins/outlook/faq-nested-app-auth-outlook-legacy-tokens)). An add-in therefore still needs Graph consent, and it adds deployment work, a localhost TLS bridge, and only runs while its pane is open.

The server-side alternatives to Graph are closing too. Microsoft began disabling **EWS in Exchange Online in October 2026**. Admins can re-enable it for allow-listed app IDs only until **April 2027**, when "EWS will not be an option that your client applications can use" ([Exchange Team Blog, 21 Oct 2026](https://techcommunity.microsoft.com/blog/exchange/exchange-online-ews-application-stopped-working-do-this-/4566215); [Microsoft Learn](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-ews-exchange-online)). EWS also needs the same Entra registration and consent as Graph, so it offers no consent advantage. EWS against Exchange Server on-premises is unaffected by the retirement ([Microsoft 365 Developer Blog](https://devblogs.microsoft.com/microsoft365dev/retirement-of-exchange-web-services-in-exchange-online/)). That is irrelevant here, though, because new Outlook still has at most IMAP-level support for on-prem Exchange with no calendar integration ([Directions on Microsoft](https://www.directionsonmicrosoft.com/microsoft-delays-by-a-year-its-new-outlook-rollout/); [CodeTwo](https://www.codetwo.com/admins-blog/new-outlook-for-windows/)). A colleague whose calendar shows up in new Outlook almost certainly has an Exchange Online mailbox, and Graph can reach it.

The rest of the industry reached the same conclusion. Sync tools built on classic Outlook COM all tell users that new Outlook is unsupported and to stay on classic: gSyncit ([Fieldston](https://fieldstonsoftware.com/support/gsyncit/topic_new_outlook_ui.aspx)), SimpleSYN ([SimpleSYN](https://simplesyn.net/en-US/note-on-the-new-outlook-app)), and Outlook Google Calendar Sync. OGCS's maintainer labelled new Outlook support "wont implement" and started a Graph-based v3 that "won't have need or make use of the New Outlook client" ([OGCS #1640](https://github.com/phw198/OutlookGoogleCalendarSync/issues/1640)). Cloud time trackers such as Toggl, Clockify, RescueTime, Timely, Rize and TimeChimp never touched the local client. They read M365 calendars through their own Microsoft OAuth apps, so new Outlook was never a problem for them. Their recurring support issue is admin approval ([Toggl Community](https://community.toggl.com/t/how-to-connect-regular-non-admin-365-users-to-toggl/3214); [Timely](https://www.timely.com/help/handbook/integrations/office-365-calendar/); [TimeChimp](https://intercom.help/timechimp/en/articles/7887831-connect-your-outlook-calendar)). The two desktop-first tools sidestep Graph instead. ManicTime uses a pasted ICS link, or an Entra app that the customer's own admin registers ([ManicTime docs](https://docs.manictime.com/server/administration/configuration/office-365-calendar)). Everhour uses ICS links ([Everhour](https://support.everhour.com/article/603-calendar-integrations)).

## An admin's one-time consent is the real gate

Delegated `Calendars.Read` is still flagged as user-consentable at the permission level. The policy most tenants run on now overrides that. Microsoft's "Let Microsoft manage your consent settings" policy (`microsoft-user-default-recommended`) "is also the default for a new tenant". Its rules let end users consent to delegated permissions **except** a list that includes **`Calendars.Read`, `Calendars.ReadBasic`, `Calendars.ReadWrite`, `Calendars.Read.Shared` and `Calendars.ReadWrite.Shared`**, alongside Mail, Chat, OnlineMeetings, MailboxSettings and, since mid-2026, Contacts, Tasks and People ([Microsoft Learn: Manage app consent policies](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies)). The only exemptions are a short allow-list of mail clients: Apple Mail, Spark, eM Client, Thunderbird and two Android clients. The calendar block arrived in November 2025 ([Topedia](https://blog.topedia.com/2025/11/microsoft-managed-default-app-consent-policy-now-blocks-20-additional-permissions/)). Vendors confirm it in practice. CalendarBridge states that since then "all third-party apps require administrator consent before a user can grant the app access to their calendars" ([CalendarBridge](https://help.calendarbridge.com/group-admin-docs/approve-delegated-permissions-for-calendarbridge-for-microsoft-365/)).

Two consequences follow. First, choosing `Calendars.ReadBasic` instead of `Calendars.Read` **does not avoid admin consent**, because both are on the list. ReadBasic is still the better request: it is the least-privileged scope for calendarView, and it withholds body, attachments and extensions ([Microsoft Learn: List calendarView](https://learn.microsoft.com/en-us/graph/api/user-list-calendarview?view=graph-rest-1.0); [Permissions reference](https://learn.microsoft.com/en-us/graph/permissions-reference)). That makes it easier for IT to approve. OGCS users show the opposite effect: they were refused when the app asked for write scopes to sync work data elsewhere ([OGCS discussion #1883](https://github.com/phw198/OutlookGoogleCalendarSync/discussions/1883)). Second, the policy text contains no exemption for apps "registered in your tenant". Expect even an in-house registration to hit "Need admin approval" under the managed default. This is an inference from the policy wording, and nobody has tested it in a real tenant. The cheapest way to find out is to try a sign-in. A tenant that explicitly kept a custom or legacy "allow user consent" setting is reported to be unaffected ([Topedia, May 2026](https://blog.topedia.com/2026/05/microsoft-managed-default-app-consent-policy-will-block-8-additional-permissions/)), so self-consent can still work there.

Because colleagues all sit in one company tenant, the right registration is **single-tenant, in that tenant**, created or approved by IT. Configure it as a public client: the "Mobile and desktop applications" platform, "Allow public client flows" enabled, and no secret. Microsoft's guide covers this platform for Electron-style desktop apps, and Tauri fits the same description ([Microsoft Learn: Redirect URI best practices](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url)). Single-tenant avoids the multi-tenant problems. Publisher verification needs a Microsoft AI Cloud Partner Program account and a non-`onmicrosoft.com` domain, which an individual developer won't have ([Microsoft Learn: Publisher verification](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview)). Unverified multi-tenant apps also draw consent warnings or blocks in other tenants. An admin grants tenant-wide consent once, for example with an authorize request using `prompt=consent`, after which "no other users in the tenant are prompted for consent" ([Microsoft Learn: Multitenant apps](https://learn.microsoft.com/en-us/entra/identity-platform/howto-convert-app-to-be-multi-tenant)). If IT wants to limit who can use the app, they can set "Assignment required", as CalendarBridge recommends ([CalendarBridge](https://help.calendarbridge.com/group-admin-docs/restrict-calendarbridge-access-to-certain-microsoft-365-users/)). The request to IT should be short and specific. Following the vendor pattern, it should say: delegated only, `Calendars.ReadBasic` plus `offline_access`, read-only, and data stays on the user's machine.

Do not borrow a Microsoft client ID to dodge this step. IDs such as Microsoft Office (`d3590ed6-…`), Azure CLI (`04b07795-…`) and Graph Command Line Tools (`14d82eec-…`) are public clients and technically usable. Sign-ins with them appear in the tenant's logs as Microsoft apps and match published phishing detections. Elastic ships a rule for "OAuth Phishing via First-Party Microsoft Application" ([Elastic](https://www.elastic.co/docs/reference/security/prebuilt-rules/rules/integrations/azure/initial_access_entra_id_oauth_phishing_via_first_party_microsoft_application)). Device-code phishing with the Office ID is a documented attack pattern ([TrustedSec](https://trustedsec.com/blog/the-new-hotness-in-phishing-device-code-attacks-in-m365)). Admins can disable these apps or target them with Conditional Access ([ourcloudnetwork](https://ourcloudnetwork.com/protect-microsoft-graph-powershell-logins-with-conditional-access/)). Microsoft also changes their behaviour without regard to third-party reuse, as the Azure AD Graph retirement for old Azure CLI builds showed ([Microsoft Tech Community](https://techcommunity.microsoft.com/blog/azuretoolsblog/azure-ad-graph-api-retirement-action-required-for-older-versions-of-azure-cli-an/4562225)). Graph CLI's calendar access is not pre-granted in every tenant anyway, so the borrowed ID would not reliably bypass consent. NeoMutt's own docs call ID borrowing "a temporary punt for end-user experimentation", not a way to configure software for other people ([NeoMutt README](https://raw.githubusercontent.com/neomutt/neomutt/main/contrib/oauth2/README.md)). On a work account, the realistic outcome is a security-team escalation against the colleague.

## Browser sign-in with PKCE beats device code and defers WAM

Microsoft supports three interactive flows for a desktop public client: authorization code with PKCE in the system browser, the WAM broker on Windows, and device code. **Device code is the wrong default in 2026.** Microsoft describes it as a flow for "input-constrained devices", and advises tenants to "get as close as possible to a unilateral block" on it through Conditional Access ([Microsoft Learn: Block authentication flows](https://learn.microsoft.com/en-us/entra/identity/conditional-access/policy-block-authentication-flows)). Microsoft also rolled out a managed Conditional Access policy that blocks it in tenants that do not use it ([Microsoft Learn: Managed policies](https://learn.microsoft.com/entra/identity/conditional-access/managed-policies)), and the CIS M365 v6 L1 baseline requires a block ([Tenable CIS audit](https://www.tenable.com/audits/items/CIS_Microsoft_365_Foundations_v6.0.1_L1_E5.audit:9033824c949b5560f26fa3d7bc1af197)). Keep it, at most, as an opt-in for a CLI running over SSH.

**Auth code + PKCE with a loopback redirect** is the default that works on Windows and macOS with no broker dependency. Entra treats loopback per RFC 8252. `http` is accepted for localhost, and the port "is ignored for the purposes of matching a localhost redirect URI". Register `http://localhost` once and bind an ephemeral port at runtime. Do not register several URIs that differ only by port ([Microsoft Learn: Redirect URI best practices](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url)). Microsoft prefers `127.0.0.1` over `localhost`, but the portal will not accept an `http://127.0.0.1` URI; you have to add it by editing `replyUrlsWithType` in the manifest. Whether the port-agnostic matching also applies to `127.0.0.1` is unverified, so test it before relying on it. Use the system browser, not an embedded webview, so existing SSO cookies, passkeys and Windows Hello work. Thunderbird moved its Microsoft sign-in to the system browser in 2026 for the same reasons ([Mozilla SUMO](https://support.mozilla.org/en-US/kb/microsoft-oauth-authentication-and-thunderbird-202)). Use the tenant-specific authority `https://login.microsoftonline.com/{tenant-id}/oauth2/v2.0/{authorize,token}`, not `/common`. That avoids personal-account edge cases and keeps the single-tenant registration honest ([Microsoft Learn: Multitenant apps](https://learn.microsoft.com/en-us/entra/identity-platform/howto-convert-app-to-be-multi-tenant)).

**WAM is the second phase, not the first.** Microsoft prefers it on Windows because it provides silent sign-in as the Windows account, Windows Hello and FIDO, and device-bound refresh tokens ([Microsoft Learn: MSAL.NET WAM](https://learn.microsoft.com/en-us/entra/msal/dotnet/acquiring-tokens/desktop-mobile/wam)). It can also be the only way to satisfy "compliant device" or Token Protection Conditional Access from a native app. That last point is inferred and not documented for third-party unpackaged apps. From Rust it is feasible through the `windows` crate (0.62.2) and WinRT `Windows.Security.Authentication.Web.Core`. askWAM-rs and an IronRDP pull request show it working ([askWAM-rs](https://github.com/Harrison-Wells-Cyber/askWAM-rs); [IronRDP #2247](https://github.com/Devolutions/IronRDP/pull/2247)). The costs are real, though: no maintained library exists, the app must register `ms-appx-web://Microsoft.AAD.BrokerPlugin/{client_id}`, and interactive requests require the parent window's HWND ([Microsoft Learn: WAM](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-acquire-token-wam)). That ties interactive WAM to `desktop/` and rules it out for a headless CLI. Add it later as a Windows `*_impl` token provider, and only if the company's Conditional Access rejects the browser flow.

Token lifetimes are friendly to a background collector. With `offline_access`, a public client receives a refresh token with a **90-day inactivity window** and no maximum age. The token "replace[s] [itself] with a fresh token upon every use". The old token is not revoked, so the app should store the new one and delete the old ([Microsoft Learn: Refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)). Admins cannot shorten these lifetimes; they control re-prompts only through Conditional Access sign-in frequency ([Microsoft Learn: Configurable token lifetimes](https://learn.microsoft.com/en-us/entra/identity-platform/configurable-token-lifetimes)). The old token surviving rotation has a useful side effect here: if the CLI and the desktop app refresh at the same moment from the same stored token, both succeed. The race is harmless. Password resets, admin revocation, or a tenant sign-in-frequency policy will occasionally force a new interactive sign-in, so the provider must report "sign in again" as an unavailable state rather than an error.

## A Graph provider that fits instants and the per-day cache

The repo's architecture already fits Graph well. Add a new provider, for example a "Microsoft 365 calendar" source, beside the COM-based `OutlookProvider`. Declare it with `cache: CachePolicy::api()` like `GitLabProvider`, and leave the existing collector untouched. The cache's runtime asks the provider for a span of whole UTC days `[start_of_day(first), end_of_day(last))` and buckets the returned entries by the UTC day of their timestamp (`core/src/cache/mod.rs`). Graph's `startDateTime`/`endDateTime` "are interpreted using the timezone offset specified in the value" and are unaffected by the `Prefer` header ([Microsoft Learn: List calendarView](https://learn.microsoft.com/en-us/graph/api/user-list-calendarview?view=graph-rest-1.0)). The request can therefore pass RFC 3339 `Z` instants straight through, with no local time zone in `core`, which satisfies the instants-only rule. One request per missing span, paged, looks like this:

```http
GET https://graph.microsoft.com/v1.0/me/calendarView
    ?startDateTime=2026-11-16T00:00:00Z&endDateTime=2026-11-17T00:00:00Z
    &$select=id,iCalUId,subject,start,end,isAllDay,isCancelled,showAs,type,
             seriesMasterId,responseStatus,organizer,isOrganizer,location,
             onlineMeeting,isOnlineMeeting,webLink,sensitivity,categories
    &$top=100
Authorization: Bearer {access_token}
Prefer: outlook.timezone="UTC", IdType="ImmutableId"
```

calendarView already returns "the occurrences, exceptions, and single instances" of events in the range. That means **no RRULE expansion in Rust**, which is the main advantage over ICS. Follow `@odata.nextLink` until it is absent, and set `$top` explicitly, because the default page size is undocumented on the page. With `Prefer: outlook.timezone="UTC"`, `start.dateTime` comes back as a naive string such as `2026-11-16T09:00:00.0000000` with `timeZone: "UTC"` ([Microsoft Learn: event resource](https://learn.microsoft.com/en-us/graph/api/resources/event?view=graph-rest-1.0)). It has no offset and seven fractional digits, so parse it as a `chrono::NaiveDateTime` and attach UTC rather than parsing it as RFC 3339. calendarView returns events that _overlap_ the window. An event that started before the span would therefore land in a UTC day the cache did not ask for, so keep only events whose start falls inside `[start, end)`. For an activity log, drop `isCancelled == true` and `responseStatus.response == "declined"`, and optionally drop `showAs == "free"`. How declined and organizer-cancelled meetings appear in an attendee's view is not confirmed in Microsoft's docs, so check it with real data. All-day events are anchored to midnight in their own time zone, so they arrive as odd UTC instants. Carry `isAllDay` through so the dashboard can render them in the browser's day. calendarView covers only the default calendar. Other calendars need `/me/calendars/{id}/calendarView`, which is a reasonable later config option. Skip `/me/calendarView/delta`: it needs `Calendars.Read`, forbids `$select`, covers only the primary calendar, and pins one window per sync round, which suits a per-day cache poorly ([Microsoft Learn: event delta](https://learn.microsoft.com/en-us/graph/api/event-delta?view=graph-rest-1.0)). Outlook throttling allows **10,000 requests per 10 minutes and 4 concurrent requests per app and mailbox**, and returns 429 when exceeded ([Microsoft Learn: Throttling limits](https://learn.microsoft.com/en-us/graph/throttling-limits)). Cap concurrency at four and back off on 429, honouring `Retry-After` when present. For the startup check, a calendarView request over a tiny window proves that both the token and the consent work.

For OAuth, use **`oauth2` 5.0.0**. It covers PKCE (`PkceCodeChallenge::new_random_sha256`), refresh, and the device grant, and ships Microsoft examples ([docs.rs oauth2](https://docs.rs/oauth2/5.0.0/oauth2/)). Pair it with the system browser and a loopback listener built on tokio inside `core`, so the CLI and desktop app share it. `tauri-plugin-oauth` 2.1.0 does the same job but lives in `desktop/` ([crates.io](https://crates.io/crates/tauri-plugin-oauth)). One local wrinkle: `oauth2`'s built-in reqwest backend targets reqwest **0.12**, while this workspace pins reqwest **0.13**. Disable that backend and adapt the workspace client through `oauth2`'s pluggable HTTP client, or hand-write the two form POSTs (code exchange and refresh), which are small enough to own. Reject the alternatives. `azure_identity` 1.0 has no interactive or public-client credential. `graph-rs-sdk` and `graph-oauth` have been dormant since 2025. The `msal` crate is a stub for Samba's Linux libhimmelblau ([crates.io azure_identity](https://crates.io/crates/azure_identity); [graph-rs-sdk](https://github.com/sreeise/graph-rs-sdk); [crates.io msal](https://crates.io/crates/msal)). Hand-written `serde` structs for the roughly 15 selected event fields belong in `core/src/model/`, per the repo's rules. Store the refresh token, account ID and granted scopes with **`keyring` 4.2.0** on `keyring-core` 1.x, using `windows-native-keyring-store` 1.1.0 for Windows Credential Manager ([crates.io keyring](https://crates.io/crates/keyring); [docs.rs windows-native-keyring-store](https://docs.rs/windows-native-keyring-store/latest/windows_native_keyring_store/)). Credential Manager caps a blob at **2,560 bytes**, and keyring counts UTF-16 bytes, so only about 1,280 ASCII characters fit. Entra refresh tokens can be larger than that ([keyring source](https://docs.rs/crate/keyring/2.3.3/source/src/windows.rs)). Either split the token across several entries, or write a DPAPI-encrypted (`CryptProtectData`) file in the app data directory. Never put tokens in the cache directory. Avoid `tauri-plugin-stronghold`, which a Tauri maintainer called "no longer recommended" ([tauri discussion #7846](https://github.com/orgs/tauri-apps/discussions/7846)). Access tokens can stay in memory, since they live 60–90 minutes.

## Published ICS is the fallback if IT refuses

If no admin will consent, the only option that needs no admin is a calendar the user publishes. In OWA or new Outlook, the user opens Settings > Calendar > Shared calendars > Publish a calendar, which yields a secret ICS URL at one of three detail levels: "Can view when I'm busy", "Can view titles and locations", or "Can view all details" ([Microsoft Support](https://support.microsoft.com/en-us/outlook/share-your-calendar-in-outlook-on-the-web)). The tenant's `Anonymous:` sharing-policy entry caps that level and can disable publishing outright ([Microsoft Learn: Set-SharingPolicy](https://learn.microsoft.com/powershell/module/exchange/Set-SharingPolicy)). Users commonly find only the busy-only level on offer ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/4695885/how-do-i-publish-my-calendar-to-show-more-than-can)), and sources disagree on what Exchange Online allows by default ([Sikich](https://www.sikich.com/?p=23276); [c7solutions](https://c7solutions.com/?p=5159)). The user can check what their tenant allows by opening that dialog. Busy-only blocks with no titles add little to an activity log. The URL is also a bearer secret that exposes the calendar outside the tenant, which many security teams dislike more than a scoped Graph consent. If the app supports ICS, store the URL in the keyring like a token. Expect to implement RRULE expansion and time-zone handling for the feed's own `TZID`s, which is the only part of this that is not trivial. Microsoft does not document how quickly a published feed reflects changes.

ManicTime's "bring your own registration" pattern is another escape hatch. A settings field for client ID and tenant ID lets the app work under any registration IT is willing to create, without a code change. GNOME Online Accounts, Evolution and DavMail all expose this setting for the same reason ([DavMail FAQ](https://davmail.sourceforge.net/faq.html); [UWaterloo KB](https://uwaterloo.atlassian.net/wiki/spaces/ISTKB/pages/44816171143/Gnome+Online+Accounts)). Classic Outlook through the existing COM collector remains a legitimate path for everyone who can run it, this user included, once the Activity Log crash with classic Outlook running is fixed. It is supported until at least 2029, and the enterprise opt-out phase was pushed to 2027 ([The Register](https://www.theregister.com/2026/03/06/microsoft_outlook_migration_postponed/)). A later "cutover" phase will remove the toggle back to classic, and no date has been announced for it. COM is therefore a bridge, and Graph is the long-term source. The practical order for someone on new Outlook is: classic Outlook with COM if they are willing to switch, Graph once IT consents, and ICS only if consent is refused and they will not switch.

## Conclusion

New Outlook turns a client-integration problem into an identity-governance problem. The code for a Graph calendar provider is a few hundred lines that fit the existing provider, cache and instants-only design almost exactly. The deciding factor is whether one Entra admin will approve one read-only, single-tenant app. Since November 2025 that approval is required even for an app registered in the company's own tenant, so the most valuable early work is the request to IT, not the Rust code. That request should state exact scopes, that access is delegated, that data stays local, and include a ready-made consent link.

Two unknowns should be settled empirically before investing further. The first is whether the company tenant runs the Microsoft-managed consent policy at all: one sign-in attempt either shows a consent screen or "Need admin approval". The second is whether its Conditional Access accepts a system-browser sign-in from an unmanaged native app. If it does, browser + PKCE is enough on both Windows and macOS. If it does not, WAM becomes necessary rather than optional, and the Windows token provider grows its own `*_impl` module. Either way, the Graph provider would also give macOS users a calendar source that no longer depends on which Outlook client is installed.
