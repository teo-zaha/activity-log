# AGENTS.md

This file defines the working rules and architecture expectations for agents editing this repository.

## Overview

`activity-log` is split into a Rust backend workspace plus an Angular frontend:

- `core/`: shared Rust library with models, collectors, cache, merge logic, markdown export, and TypeScript generation
- `api/`: Rocket HTTP API
- `cli/`: Rust CLI package containing the user-facing collection binary and the TypeScript generator binary
- `dashboard/`: Angular application that consumes generated backend DTOs
- `desktop/`: Tauri desktop shell that wraps the Angular app and talks to Rust commands

The backend contract is owned by Rust. The frontend consumes generated DTOs and should not redefine backend models by hand.

## Project Architecture

### Rust workspace

- `core/src/model/`: shared models grouped by domain/source. An `ActivityEntry` is read by its wire `source` (`ActivityEntry`'s own `Deserialize`): an object is read as the kind it names, with that kind's fields, or refused (B38). Each entry struct's `source` is that kind's tag (`model/activity/source_tag.rs`, one macro for the six zero-sized tags, the one file with several types), so a struct can only name its own kind; `timestamp` is a `Timestamp` (`model/common/timestamp/`: the RFC 3339 text as the source wrote it, sent back unchanged, and the instant it names; text that names no instant makes none). Outlook and calendar entries flatten one `MeetingBody` (duration, busy status, weight, description, join link; `ActivityEntry::meeting`). What a source does not have is absent, never `""`, `"unknown"` or a placeholder (a Git commit's `branch`, a GitLab push's `title` and `targetType`, a meeting's `title`: the UI and the export show `(No title)`). `connection` is a `ConnectionName` (`model/activity/connection_name/`): unstamped in a collector's entry, stamped by `ProviderRuntime::collect` with a `ConnectionStamp` (never empty) before the day cache stores it; only a stamped name is serialized and only a non-empty one is read, so no entry is stored, sent or accepted without one. `core/src/model/activity/activity_entry/tests.rs` pins every kind's wire bytes
- `core/src/model/change_stack/`: `ChangeStack`, where a change (a GitLab merge request, later a GitHub pull request) stands among its repository's open changes as the host has it now, not on the entry's day: one wire type every code host's entries carry (`GitLabEntry.changeStack`), its parts one per file. It holds the change itself (`current`), what it builds on (`below`, from the base up), a typed `bottom` (`reached` with its branch, `ambiguous`, or `cut`) and the tree `above`, whose every level ends `complete` or `cut` (`StackCut`: `limit`, `unreadable`, `throttled`, `failed`, `cycle`). Made only by `ChangeStack::new`, which reading one runs too (`try_from`): more than its change alone, no blank title or branch, `http(s)` links without user info, no change twice on one path. Absent when the change is not open, stacks with nothing, or its openness could not be told
- `core/src/collect/`: one collector per source, and what several share: `meeting_text/` (a meeting description's readable text and its join link, for the calendar feed and Outlook) and `change_stack/`
- `core/src/collect/change_stack/`: change stacks whatever the code host, with no host's code in it: which open changes a change builds on and which build on it, by the branches they come from and go into. A host implements `ChangeLookup<R>` over its repository key (GitLab's project id; `open_page`, `open_numbers`, `open_from`, `open_into`, `concurrency`), and `change_stacks` does the rest for one connection. `lookup/`: the trait, `OpenChange`, `OpenPage` (`Complete` or `Partial`) and `LookupFailure` (a `FailureKind`: `Unreadable`, `TokenInvalid`, `ScopeMissing`, `Throttled`, `Limit` or `Failed`, with its typed `LookupCause`: the request's `ApiError`, a repeated page or an ignored filter). `budget/`: one connection's `Budget` for one collection, `STACK_REQUESTS` (50) reserved atomically before each request and the `STACK_BUDGET` deadline (20 s), past which a lookup is `Limit`; its breaker, tripped by a refused token, a missing scope or a busy host, refuses every later request with that reason. `walk/`: a repository's first page answers every walk there from memory when it holds all its open changes; otherwise openness is asked by number and each branch question once (a single-flight memo, failures included). Below is walked down to the base (`ambiguous` where several open changes come from one branch), above breadth-first, children by number; `STACK_DEPTH` (12) per direction and `STACK_MEMBERS` (30) per stack end it with `limit`, a change already on its path with `cycle`, a failed lookup with its cut (a refused token or scope shows as `unreadable`); a change whose walk never started is `cut{limit}` both ways, never shown as not stacked. Changes are walked newest event first, so the result depends on no map's or server's order. It all runs inside the caller's future (no task is spawned), so dropping it stops every request; one summary line per connection, and one warning per kind of failure with its counts and first cause. `web_link/`: a change's link is kept only when it leads to the host's web origin (`Unshown::Elsewhere` with the origin it led to, or `NotAWebPage`)
- `core/src/lib.rs`: orchestration entry point used by both `api` and `cli`; numbers ids a source repeats (`id#2`), so `(source, connection, id)` names one entry (the runtime stamped `connection`). `collect_connection` runs one connection's collection under `COLLECT_TIMEOUT` (120 s), logs it (`Collected N entries in … ms`), and then, after the day cache and outside that timeout, its `annotate` step (`ProviderRuntime::annotate`) under `ANNOTATE_TIMEOUT` (`STACK_BUDGET` + 2 s), a safety net for an adapter that overruns its own deadline: entries are only lent to it, so none is lost when it is stopped, and what it adds (change stacks) is never cached and reaches days the cache served too. The connection settles only after it, so a GitLab connection with merge request events can stay `pending` up to about 22 s longer than its collection took (the CLI waits as long)
- `core/src/aggregator/`: builds an `ActivityLog` from per-connection results: folds GitLab pushes into their git commits (by `GitLabEntry.pushedCommit`, one push per commit, the earliest by instant, then connection and id: another push of the same commit stays an entry), sorts, counts, and shows what pending connections carry (`carried_for`, without a commit a finished connection has)
- `core/src/runtime/`: `Host` (`runtime/host/`), the collection state shared by `api` and `desktop`, one per process: the installed config's connections and their checks, the collection on screen, config edits (`Host::edit`, through `settings::edit_config`) and reloads (`reload_if_changed`, by content id; `watch_config` looks every 2 s and installs a change another writer made once it read the same twice 200 ms apart; a file that does not parse is logged once and the last good config stays), and the published state (`subscribe`: a `watch` of `Published`: the host's `epoch`, the `authority` that each config install and each collection key a check replaces (`KeyChange::Replaced`: another account than entries may be shown for; a first answer after an install is `First` and no boundary) raise and stamp both parts with, so the checked provider and the eviction of the old account's entries reach a subscriber as one pair, and activity and providers with a host-wide revision per part; `runtime_state` reads it as one `RuntimeState`, both parts of one moment; `feed` gives one subscriber a `Feed`: the current value, then the latest after each change, values in between skipped, until shutdown). `runtime/forward/`: what a subscriber of the feed is sent (`docs/plans/shared-contracts.md` §5): a `Forwarder` per subscriber makes a `state` pair due first, after an authority it was not sent and after `reset` (a failed delivery), and otherwise each part whose revision rose (`Due`); each accepted message is acknowledged on its own; `take` hands everything due in revision order; `RuntimeMessage` is the event name and its DTO's compact JSON, `ping` (`RuntimePing`, the host's epoch) included, which no forwarder makes due. The SSE route and the desktop's events both use it. Every transition is decided, installed and published under one short state lock; a run or a check that is no longer current changes nothing (run ids and check generations are host-wide). Work goes to the adapter's `RunSpawner` only after the lock is released, so each command answers with the state it installed and that part's `PartStamp` (`Answered`: `collect` running, `recheck` checking; an edit's new connections checking with its `InstallReceipt`, `None` when the file was written but the host shut down before it installed it (B70): the save is durable, no revision shows it); a run's work resolves to its `RunEnd` once its end shows (`is_current` tells whether it still does), a check's to `None`. `collect`: a running collection of the same range goes on, another range replaces it. `recheck` runs one connection's check again and collects its kind again for the range on screen (a running collection starts over, a failed one runs whole). An install collects again only the kinds it affects (`affected_kinds`: a connection added, removed, reordered, with other values, location or table `instance` (removed and added again; a legacy table's first instance is no change), or with no outcome yet); a running or failed collection runs whole, and a label edit still collects a kind whose fresh check finds another account. A check is recorded before any collection uses it; a recorded key change also clears that connection's failure. Nothing is logged under the state lock: a transition's lines are emitted after it is released (tests assert it). `shutdown` is the last transition: the shown run stops, runs and checks still in flight are no longer current (a run ends `Stopped`, a check publishes nothing, `is_current` is false), and no edit or reload installs anything; the spawner is dropped, and the config watcher and every feed end. `runtime/report/`: what a run reports per connection (`RunReport`, `Slot`, `Outcome`, `Stored`; a failed connection's `CollectFailure`: its problem, `timedOut`, `refused` and `unreachable` told apart from `collectionFailed` by the `RemoteFailure` (`provider/remote_error/`, the `ApiError` a collector's request ended with, kept in its `anyhow` chain) or the collection's timeout, and its message) and the `Collector` that produces it (`collect_planned` in production; a run does not fail as a whole: only a panic ends one failed); `runtime/result_store/`: the shown run's report, from which the log is folded (`RunReport::project`) and the next run's plan is taken (carry, keep); `runtime/keys/`: each connection's `CollectionKey` (values, location and the identity its check found: `Verified`, a new one for every `Unnamed` check, `Denied`; no answer keeps it), so entries collected under one key are never carried, kept or shown under another. A connection whose last collection failed is listed `degraded` with its failure's problem and the error as its reason; a label edit keeps that
- `core/src/provider/`: one adapter per source kind (`provider!` declarations: supported OS, typed config, which the startup check gets resolved, cache policy, startup check, collect, and optionally `annotate`: what is true now rather than on the entries' days, added to one connection's collected entries, infallible, fields only, written in one pass after every await; `provider::adapter(source)` and `provider_registry()`, built once, in `Source` order), the per-connection `ProviderRuntime` and the typed startup problem (`ProviderInfo.problem`; a check ends in a `CheckOutcome`, `Available`, `Degraded` or `Unavailable` with its problem and reason, which `CheckOutcome::apply_to` writes into `ProviderInfo` together with `usable` and `recheckable`: any problem but `unsupported` can be checked again; a refusal of the credentials is `refused`, a server out of reach `unreachable`; `provider/source_failure/`: `problem_of` reads the problem from the typed causes in an error's chain, `RemoteFailure`, `SourceFailure` (`SourceProblem`: `notInstalled`, `notRunning`, `permissionDenied`, `noData`) and an `AppleScriptError`'s number, for `ProviderCheckResult::unavailable_from` and `CollectFailure::of`)
- `core/src/provider/{jira,gitlab}/api/`: `JiraApi` and `GitLabApi`, the only way the Jira and GitLab checks and collectors reach their servers (`remote_api/` holds the shared client). Paths are built from segments and query values through `query_pairs_mut`, never with `format!`; credentials go only to the configured origin (a redirect elsewhere stops, a URL with a user name or password leaves the connection not configured); every failure goes through `remote_error/` (`ApiError`, `remote_message`: the server's own message only, secrets redacted, addresses without user info or query, control characters escaped, at most 300 characters; error bodies are read only in part); a refusal (401/403) is decided by its status (`ApiError::problem`); an error answer's RFC 6750 code (`OAuthRefusal`: `invalid_token`, `insufficient_scope`, `invalid_request`, from `WWW-Authenticate: Bearer` or the body's `error`) is kept on `ApiError::Status` for callers that tell a refused token from a missing scope; a body that breaks off is a transfer failure, never an unreadable answer. The startup check parses its identity request (Jira `/myself`, GitLab `/user`) into `IdentityEvidence`, which `ProviderRuntime::identity()` keeps; for GitLab that is the token's owner, not the configured user whose events are collected. `RemoteClient` retries a busy answer as its caller's `Retry` says: `OnceShort` (once, when the server asks to wait at most 10 s; collections and checks) or `Never` (the change stack lookup, which stops at the first). `provider/gitlab/api/pager/`: GitLab's paged lists (`Pager`), shared by the collector and the lookup: each page is paid for with a `RequestBudget` before it is sent (`Unmetered` for a collection), and a list that names a page it already sent or sends only rows already read stops (`PageError::Repeated`); `api/merge_requests/`: a project's open merge requests by a `MergeRequestFilter` (all, numbers, from or into a branch; never empty or blank, which GitLab would read as no filter), each row checked against the question (`RowFit`)
- `core/src/provider/gitlab/stack/`: GitLab's side of change stacks, `GitLabChanges` (`ChangeLookup<u64>` over `GitLabApi`, 4 requests at once, numbers 50 per request) and `annotate`, which looks up the stack of every merge request event's change (`projectId`, `mrIid`; never a push, which folds into a commit) and then writes it on every GitLab entry, clearing it where there is none. Requests are `Retry::Never`; a failure's kind comes from the OAuth code first (`invalid_token`, `insufficient_scope`; `invalid_request` is `Failed`), then the status (401 a refused token, 403 and 404 a project hidden from it, 429 and a 503 with `Retry-After` a busy host). A row of another project, number or branch fails its list (the filter was ignored); one no longer open (`locked` while it merges) is left out and counted in one line. A link to another origin than the configured URL's is dropped and counted, and one warning per collection names the count and the origin GitLab linked to (scheme, host and port)
- `core/src/platform/`: OS integrations shared by collectors (Windows COM/event log, macOS AppleScript run in its own `osascript` process, so a timeout or a stopped collection kills it); `platform/dirs` holds the OS settings and cache folders; `platform/blocking` runs blocking OS work (Git walks, `wsl.exe`, Outlook COM, the event log) on a thread with a flag set once nobody waits, so it stops and kills the process tree it started (a process group, a job object on Windows), and lets one job at a time reach each resource; work that stops so ends with the `Stopped` error, told apart by its type (`err.is::<Stopped>()`); `platform/private_file/` writes files only the current user can open (settings, the cache): `Folder::replace` writes a file created private inside a verified owner-only staging folder beside the target, flushes it and moves it over the target through folder handles (on Windows `NtSetInformationFile`'s rename relative to the parent's handle, since the Win32 `SetFileInformationByHandle` refuses a `RootDirectory`), and a failure names its step (`ReplaceError::Failed` with its `ReplaceStep`) and leaves the target as it was. Names are single entries of a folder, on Windows also ones Win32 and NT read alike (no trailing dot or space, no device name such as `CON` or `COM1`). A location that cannot keep files private (FAT, exFAT, network shares, a folder other accounts can write to) is `Unprotectable` before anything is written. Its OS modules are chosen with a compile-time `imp` alias. `platform::parsed_output_command` starts a subprocess whose output is parsed in the C locale (`last`, `pmset`, `osascript`, git's `user.email` fallback); the WSL script exports `LC_ALL=C` itself, since `wsl.exe` passes no environment in
- `core/src/export/`: renders an `ActivityLog` as JSON or Markdown (`render_export`; `export/markdown/` escapes every text from a source so it cannot change the document's structure) for the CLI, the desktop save dialog and `POST /api/export`; days and times in the zone the caller passes
- `core/src/ts/`: generated TypeScript contract source, and the constants the dashboard checks as the backend does (`COLLECT_MAX_DAYS` from `CollectOptions::MAX_DAYS`, `BACKEND_ERROR_KINDS`, `SOURCES` from `Source::iter()`, whose strum names are its serde names; `DESKTOP_COMMANDS` and `DESKTOP_EVENTS` from `core/src/ipc/`, `RUNTIME_EVENTS` from `RuntimeMessage::EVENTS`)
- `core/src/ipc/`: the names of the desktop app's commands and its own events, the one place they are spelled (the menu's are in `core/src/menu/`). Tauri names a command by its function, so `desktop/src/tests.rs` invokes every name here and the menu's through the app's own handler (`app_commands!` in `desktop/src/lib.rs`) and checks it takes each
- `core/src/model/common/backend_error.rs`: `BackendError { kind, message }` (`message` sent as `error`), what every API error body is and every desktop command fails with; `kind` is the generated `BackendErrorKind` union (`noData`, `invalidRequest`, `notFound`, `alreadyExists`, `busy`, `conflict`, `noLocation`, `unprotectable`, `badConfig`, `tooLarge`, `internal`). `core/src/backend_error/` is the one place core's typed errors get their kind (`From` for `RangeError`, `ExportError`, `ConfigEditError`, `ConfigError`, `LoadError`, `EditError`); `runtime::answer_collect` and `runtime::answer_recheck` are the collect and recheck answers the API and the desktop both give
- `core/src/utils/`: `now_iso`, `stable_id` (FNV-1a) for entries whose source has no id, `random_u64`
- `core/src/cache/`: per-day disk cache for remote API providers. A provider opts in with `cache: CachePolicy::api()` in its `provider!` declaration; the runtime then fetches only the runs of missing or stale days. A file holds each day's entries as they are sent, read by their `source` (version 7, GitLab entries with their `projectId`; a file of an older version is fetched again and replaced, one of a later version left alone). One file per connection and verified principal (`ProviderRuntime::cache_scope`: the safe fingerprint, URLs as their endpoint, plus the check's `RemoteIdentity`); without a verified identity, or with a query or fragment in a URL, the connection is collected uncached (a URL with a user name or password leaves the connection not configured, so it is not collected at all). A folder that fails `Folder::check_private` is neither read nor written. Each run of stale days is written as soon as it is fetched: without a lock during the fetch, then under `{file}.lock` re-read, merge only its days (newer `fetched_at` wins, ties keep the stored day) and publish an owner-only file through `platform::private_file`; a file that does not decode or is of a later version is left alone (a later version's file is reported by each collection that finds it). The folder is checked again once the lock is held. Cache I/O runs on `spawn_blocking`. Files live in the OS cache dir (`ACTIVITY_LOG_CACHE_DIR` overrides it), never the working directory
- `core/src/diagnostics/`: in-memory diagnostic log (ring buffer) shown in the settings Logs pane; use `diagnostics::info/warn/error` instead of `eprintln!` so messages are visible in the desktop app
- `core/src/provider/connection/`: a provider kind can be configured more than once; each setup is a connection (`ConnectionId { source, name }`) with its own values, runtime, status, cache file and log scope. An adapter declares `instances()` (one or several connections) and optionally `collection_state()`/`finish_kind()` for work across its connections (Git matches emails found in all of them). Collectors stay unaware of connections: the runtime stamps `connection` on entries and scopes log lines. Each connection runs its own check → collect pipeline (`collect_planned` in `core/src/lib.rs`, which reports each connection's entries; `collect_runtimes` for the CLI, whose `RunReport` says how each connection ended), and the report is rebuilt each time one settles, so `finish_kind()` also runs provisionally (`complete: false`) while connections of its kind are pending and must then return a subset of its complete result
- `core/src/settings/`: `config.toml`, the connections file shared by the CLI, the API server and the desktop app (`[[gitlab]]` tables, field names without the kind prefix). It is the only list of sources: a kind it does not mention has no connections, and environment variables never configure a source. No binary reads a `.env` file: the CLI, the API server and the processes they start get only the environment they were started with, so a checkout's `.env` sets nothing (`cli/tests/settings.rs` pins it). Connection names are compared as slugs; a repeated name is numbered (`work-2`) in file order with a warning, and the next edit writes it. Read it with `load_connections`/`ConfigFile::logged_connections`, which send its warnings to the Logs pane; a table it cannot read is skipped with a warning, and edits address tables by their place in the file. Every writer goes through `settings::edit_config`: under the `config.toml.lock` lock (5 s wait, then "busy") it reads the file again, checks the writer's `Precondition` (an `EditBase` taken before any question; account fields and the table's reserved `instance` id tell a changed or re-added connection apart), applies the change, gives each table it wrote an `instance` if it has none, checks the result reads, and publishes it through `private_file` unless the bytes are unchanged. Readers never lock or write. `config edit` (`settings::edit_externally`, run by `settings::Editor`: `$VISUAL`, `$EDITOR` with its arguments read as Git reads them, `sh` on Unix; on Windows a file path, or a command line whose program is found through `PATH` and `PATHEXT`, so a `.cmd` such as VS Code's `code` starts) gives the editor a copy in a private session folder and publishes it only if the file did not change meanwhile. Parse errors name the line and column, never the file's text. Without an OS config folder and no `ACTIVITY_LOG_CONFIG`/`--config` there are no sources and every save fails with `settings::NO_LOCATION`; nothing falls back to a temporary folder

### API

- `api/src/lib.rs`: Rocket routes over a `Host` (`BadConfig::Fail`: a file that does not parse stops the server with its place), its spawner (`tokio::spawn`), the startup collection and the config watcher on liftoff, `Host::shutdown` on shutdown; the activity, providers, runtime-state, collect and recheck routes first call `reload_if_changed` (events, export and logs do not; the watcher reloads for the stream), so edits from the CLI or the desktop app apply without a restart. Every error answers a `BackendError` body with the status of its kind (`status_of`); a default catcher answers one for what Rocket refuses itself (an unknown route `404`, a body that is no JSON `400` or not the route's request `422`, a panic `500`)
- `api/src/main.rs`: runtime bootstrap

Routes:

- `GET /api/activity`: `202` with a partial `ActivityLog` while a collection runs (`meta.pending` names the connections still to come), `200` with the complete log, `200` with `CollectionFailedResponse` after a failure, `503` before the first collection
- `GET /api/providers`
- `GET /api/runtime-state`: `200` with `RuntimeState`, both parts of one moment with their stamps (`docs/plans/shared-contracts.md` §5); `activity.state` is `empty` before the first collection, never `503`. A plain read; the dashboard follows `GET /api/events`
- `GET /api/events`: `200` `text/event-stream` (Rocket's `EventStream`, its comment heartbeat off) over `Host::feed` and a `Forwarder`: a `state` event (`RuntimeState`) first, then `activity` (`ActivityUpdate`) and `providers` (`ProvidersUpdate`) as each part changes, in revision order, another `state` after each authority change, and `ping` (`RuntimePing`) after `runtime::PING_INTERVAL` (15 s, generated as `RUNTIME_PING_SECONDS`) without an event, the heartbeat a browser sees; compact JSON on one `data:` line, no `id:` and no replay. A reader that lags skips values, never a part's latest. It ends when Rocket shuts down (`Shutdown`) or the host does. This is how the browser dashboard follows the host. The dev server's proxy (`dashboard/proxy.conf.mjs`) streams it as is and ends the browser's answer when the API's breaks off (the API was killed), so the dashboard's stream sees the end; `scripts/dev-proxy.test.mjs`, run by `dashboard:lint`, pins that
- `POST /api/collect`: starts the collection and answers `202` at once with its first snapshot; a collection of the same range that already runs is answered with its snapshot, one of another range is stopped. Every answer of it is a `CollectAnswer`: the log or failure as before, plus the host's own `kind` for it (`ShownActivity`: `running`, `ready`, `failed`) and `stamp` (`PartStamp`), the activity part it installed or shows
- `POST /api/connections/recheck` with a `ConnectionId`: runs that connection's startup check again (`Host::recheck`) and answers `200` with a `RecheckAnswer` (`ProvidersResponse` and the providers' `stamp`), the connection checking; `404` (`notFound`) for one the server does not have, `500` (`internal`) once it shut down (`Host::recheck` fails with `RecheckRefused`, `UnknownConnection` or `ShutDown`)
- A request body that is not `application/json` matches no route: `404` (`notFound`), Rocket's route matching, pinned by a test
- `POST /api/export`: `ExportRequest` (format, `[start, end)`, IANA `timeZone`, entries) → `200` with `ExportFile` (`fileName`, `content`), `400` with an `invalidRequest` `BackendError` for an unknown zone, a bad range or a body that is no request, `413` (`tooLarge`) above 64 MiB (this route reads its body itself; Rocket's JSON limit is 1 MiB)
- Every range (collect, export, CLI) is checked by `CollectOptions::check`: `end` after `start`, at most `CollectOptions::MAX_DAYS` (ten years); the dashboard checks a URL's range the same way, in instants, with `collectableRange` (`utils/app-url.ts`, against the generated `COLLECT_MAX_DAYS`): `DeepLinkService` drops a link's range outside that and `ActivityViewStateService.openedRange` collects none
- `GET /api/logs`, `DELETE /api/logs`

### Desktop

- `desktop/src/app_state/`: the desktop's `Host` (`BadConfig::StartEmpty`: a file that does not parse is logged and the app opens without sources), its spawner (`tauri::async_runtime::spawn`); `lib.rs` starts the first collection and the config watcher and calls `Host::shutdown` on `RunEvent::Exit`
- `desktop/src/commands/`: Tauri commands mirroring the API, each failing with a `BackendError` (`save_export` renders through `core::export`, opens a save dialog and answers `ExportOutcome`, `saved` or `cancelled`, all off the window's thread (rfd puts the dialog on the main thread where macOS needs it), one at a time: another while one is open is `busy` (`ExportTurn`); `add_connection` answers with the `created` id; `get_runtime_state` mirrors `GET /api/runtime-state` and is the dashboard's handshake before the events; `collect` and `recheck_connection` answer as their routes, `stamp` included; saves, additions and removals answer with the `installed` receipt; a save's values are checked before the file is read, `invalidRequest` with its first issue for one that does not fit; `check_provider_config` answers a save's issues without saving; saves and removals check their `basedOn` under the write lock and are refused as `conflict`). Their tests call them over Tauri's mock IPC, as the dashboard does
- `desktop/src/runtime_events/`: `forward`, one task started in `lib.rs` over `Host::feed`, sends the host's state to the main window as the Tauri events `state`, `activity` and `providers` (`emit_str_to`, the JSON of `GET /api/events`). Tauri evaluates an event only in a webview that listens for it, so nothing reaches the window before the dashboard listens. `state` and `providers` go at once; `activity` at most every `ACTIVITY_SPACING` (250 ms), the then-current value deciding once the quiet period ends, so the window's thread is not flooded with large scripts; a failed emit resets the forwarder, is logged once, and a full pair follows after `RETRY_AFTER` (1 s). Tests drive it with paused time and a recording emitter
- `desktop/src/provider_config/`: where the desktop reads `config.toml` for the settings pane (the host's own path), and `SnapshotRegistry`: the files of the 16 latest snapshots by `revision`, in memory only, from which a save's or removal's `basedOn` becomes its `Precondition` (an unknown revision is an `UnknownBase` conflict at once)
- `core/src/settings/view/`: the settings pane's view of `config.toml` (`build_snapshot`: every kind, each connection's fields labelled as their keys declare them, `provider_config!`'s `KEY "Label": Type`) and its edits (`save_changes`, `apply_save`, `apply_add`). `normalize` is the one check and stored form of a submitted value (`Submitted::Text` or `List`), used by the desktop's saves, its `check_provider_config` and the CLI's `sources set`/`sources add`; `prepare_save` is the one pass that yields a save's normalized edits or every issue; `check_save` lists a save's issues and, against the file as it is now, what changed since its base (`ProviderConfigFieldIssueDto`: the field, as `ProviderConfigFieldRefDto` `label`, `value`, `item` or `connection`, its `problem`, `invalid`, `changed`, `removed`, `replaced` or `unknownBase`, and what to do; never a value), and a refused save says its first as `{field label}: {message}`. A value read from the file is checked by `value_problem` (`provider_config_value_matches_type`), the same rule but for user info in a URL, which only a new value is refused for, so a file that holds one still loads and its check says what to change. URLs are `http` or `https` with a host (B64)

- `ActivityDataService` is the coordinator. It installs one `Installed` state (both parts of one host) by the §5 rules. The first pair installs whole. A command's answer that comes before any pair installs its part too, but that host is unconfirmed until a pair of it comes. An authoritative pair of another epoch installs whole over a confirmed host, and over an unconfirmed one only if it is the first pair of a handshake the coordinator asked for (an older first read cannot bring back the host before); otherwise, and for a pair of another epoch that is not authoritative, it installs nothing and the source is asked for a new stream. A pair of the installed authority applies part by part, each part only past its installed revision; one of another authority installs whole only past everything installed. ## Code Quality

Working code is not done code. A change that works but misses these rules is unfinished, and a review reports each miss as a finding, not as taste. The Rust and Angular rules below apply them to each side.

- Logic never decides anything by comparing, searching or parsing text meant for people. Tell cases apart by types: enums, discriminated unions, error kinds, status codes. Messages are only for people to read
- Make wrong states unrepresentable: one union of states instead of flags or nullable fields that must agree, and an `Option` or a variant instead of a sentinel (`""`, `-1`, `"unknown"`, a shared marker string)
- One source of truth per fact: a contract is generated from its owner (Rust), a rule lives in one place, a value is derived instead of copied. When something replaces old code, delete the old code
- Types hold across every boundary (HTTP, IPC, events, the cache, generated DTOs): no casts where narrowing works, no `any`, no error strings a caller must tell apart; untrusted input is checked where it enters
- Errors keep their kind and their cause: never swallow one, never merge different failures into one
- Tests check behaviour and fail without the fix they guard; they assert kinds and results, not wording, unless the wording is the product

## Rust Rules

- Keep shared domain and API types in `core/src/model/`, not in `api` or `cli`
- Put each model struct in its own file under the matching domain/source folder
- For Rust modules with local tests, colocate them as a folder pair: `mod.rs` plus `tests.rs` in the same directory
- Do not keep Rust code in `foo.rs` while its tests live in `foo/tests.rs`; move the implementation into `foo/mod.rs` instead
- Prefer moving reusable logic into `core` instead of duplicating behavior in `api` or `cli`
- Preserve wire compatibility for public API fields unless the task explicitly changes the contract
- The backend deals in instants: requests carry a `[start, end)` range of RFC 3339 instants and entries carry RFC 3339 timestamps. `core` and `api` never read the machine's time zone, with the exceptions below. `core` may group by local day only in an IANA time zone the request carries (the dashboard sends the browser's zone, as `ExportRequest.timeZone`; the CLI passes the terminal's), as `core::export` does; the dashboard and the CLI turn local days into instants
- Exceptions: sources that report local wall-clock time without an offset, converted where they are parsed: macOS `last`, and ICS times without a zone (floating times), which `collect/calendar` reads in the machine's zone (`local_zone()`). Floating times mean the wall clock of whoever's calendar it is, the same kind of input as `last`; passing a zone in would put the reader's zone into collections and their cache, which are shared by every reader
- Errors are typed: a failure a caller must tell apart is an enum or a kind, never a `String` (`Result<_, String>`) or a message matched by text; callers decide on the kind, never on the message, which is for people. Every error crossing the backend boundary is a `BackendError`, mapped in `core/src/backend_error/`. Tests assert kinds, not wording, except where the wording is the product (redaction, the agreed texts)
- No sentinel strings as errors or absent values (`""`, `"unknown"`, a shared `STOPPED` text): use an `Option` or a variant
- A subprocess whose output is parsed runs with `LC_ALL=C` (`last` prints its dates in the user's language otherwise)
- Use comments sparingly and only where behavior is not obvious
- Keep PowerShell and subprocess integrations parity-focused unless the task explicitly replaces them
- For OS-specific Rust implementations, gate child modules at the parent boundary with `#[cfg(target_os = "...")]`
- Name OS-specific child modules by platform (`windows`, `macos`, `linux`) and keep the dispatch in the parent module
- A parent module with OS children chooses its implementation at compile time with an `imp` alias: `#[cfg(target_os = "windows")] use self::windows as imp;` (and `macos`, `linux` where they exist; one child may serve several targets, as `platform/private_file`'s `unix` does for macOS and Linux, itself using the `macos` or `linux` child, and `platform/blocking`'s does under `cfg(unix)`), plus one `fallback` module for the targets left (`#[cfg(not(any(...)))] use self::fallback as imp;`), which answers as an unsupported system would: a connection the OS cannot have checks as `unsupported` (a WSL Git connection off Windows), and a provider whose `supported_os` leaves the target out is refused before its fallback runs. A parent whose children cover every target has no `fallback`. The parent's own functions call `imp::…`, and callers outside the parent go through them, never `imp` or a platform child. An item only one OS has (a type, a helper used by another module's code for that OS) may be re-exported at the parent for callers gated on that OS (`collect::git::has_wsl_repos`), without a fallback. A function and its no-op twin (`foo_impl`) never stand in for an OS child
- `platform` is the exception: it does not choose between implementations but is a library of OS APIs, `platform::macos` and the Windows items at `platform::`, which only code gated on the same OS calls (an OS child, or a function under `#[cfg(target_os = "...")]` such as `source_failure`'s AppleScript lookup, whose twin elsewhere finds nothing)
- Keep shared cross-platform logic in shared modules; only split into OS-specific modules when behavior is genuinely platform-specific

## Angular and TypeScript Rules

- Always maximize type safety
- Errors are typed: callers narrow on a `BackendFailure`'s or `Failure`'s `kind`, never on `message`; an ESLint `no-restricted-syntax` rule (`messageDecisions` in `eslint.config.mjs`) refuses comparing, switching on, testing or searching a `.message` (also `?.message` and `['message']`) in `dashboard/src/app`, and allows showing it; `scripts/eslint-message-rule.test.mjs`, run by `dashboard:lint`, pins both
- No business logic in the dashboard: provider data, domain rules and derived results (dedupe and merging, what counts as meeting time, link finding, export formats, status semantics) are computed in Rust (`core`) and delivered through DTOs; the dashboard only formats, lays out, renders and filters what it shows. Examples: `meetingWeight` on meetings (a meeting is an entry whose adapter has one, `meetingWeight !== null`), `ProviderInfo.problem` and `recheckable`, entry `id`s, carried entries in partial logs, and exports rendered by `core::export`
- Aggregating what the dashboard shows is presentation and stays there: adding up the meeting time of the visible entries per browser-local day (`utils/meeting-time.ts`, the interval union over entries by their `meetingWeight`), counting or grouping visible entries
- Do not handwrite backend DTOs in Angular
- Do not add compatibility wrapper files that only re-export or re-import generated backend DTOs
- Keep generated files under `dashboard/src/app/generated/`
- Keep Angular-only types and helpers separate from generated backend contract types
- Prefer explicit imports from generated files for backend shapes
- Prefer discriminated union narrowing over `as` casts whenever possible
- Avoid `any`, avoid weakening types for convenience, and keep helper APIs typed as specifically as possible
- Preserve existing Angular patterns unless the task explicitly calls for a redesign
- State that should survive a reload or be linkable lives in the URL: routes for views, query params for filter, range and settings. Services read it from the router; components navigate instead of setting that state. Transient UI state (selection, hover, hidden sources, zoom) stays in services
- Browser APIs, element observers, event listeners, timers and router state use `@signality/core` composables; hand-write only when Signality does not cover the case, and say why in a comment. The version is pinned exactly while it is 0.x; read the release notes before bumping
- For responsive SCSS in `dashboard/`, use named breakpoints from `dashboard/src/app/components/_dashboard-shared.scss` (for example `@include ui.down('phone')`) instead of raw `@media (max-width: ...)` where a named breakpoint exists; TypeScript reads them through `BreakpointState`, whose widths (`utils/breakpoints.ts`) `scripts/breakpoints.test.mjs`, run by `dashboard:lint`, pins to the SCSS's
- For shared dashboard content width caps, use `var(--content-max-width)` instead of hardcoded pixel values (for example `1120px`)
- Every theme's text reads at WCAG AA for normal text: `--text-primary`, `--text-secondary` and `--text-tertiary` reach 4.5:1 on `--bg`, `--surface`, `--surface-alt` and `--surface-hover`, in that order of contrast. The light themes darken the accent under white; the dark ones keep it light and draw `var(--bg)` on it. `--brand` is the logo's blue (`favicon.svg`): Light's accent and Dark's primary button; both draw the brand mark as the app icon's gradient (`--brand-bright` to `--brand-deep`). `scripts/theme-contrast.test.mjs`, run by `dashboard:lint`, reads each theme's tokens in `styles.scss` as the app's `html` gets them (`html[data-theme='…']`'s rules, then `html.dark`'s for a theme in `DARK_THEMES`, then `:root`'s; the settings' swatches left out) for every theme in `THEMES`
- Hover styles go through `ui.hover` (`components/_dashboard-shared.scss`), written inside the control's rule: `@media (hover: hover)`, so a tap on a touch screen leaves no control looking hovered, not after a touch on a device that has a mouse too (`html.touch-input`, kept by `utils/touch-input.ts` until a mouse moves; the guard sits on the control itself, `:not(:root.touch-input *)`, so Angular's style scoping keeps it), and the same look at once while the control is pressed (`:active`; `$pressed: false` for a reveal or a field). A scroller sets `overscroll-behavior` beside its `overflow`, on itself, for each axis it scrolls (`auto` where it hands its scrolling on, such as a list inside a scrolling pane). `scripts/touch-styles.test.mjs`, run by `dashboard:lint`, pins the compiled mixin and refuses a raw `:hover` or a hover media query outside `ui.hover` and `ui.no-hover` (what a touch screen changes, such as the room a finger needs, or hides, such as the resting Shift tag, which it pins) and a scroller without it in every stylesheet (inline `styles` too, read with the TypeScript parser), names a stylesheet it cannot read, checks the viewport meta (`viewport-fit=cover`, pinch zoom kept), and pins the compiled `ui.field-text`. What a layout makes of the styles is checked in a browser: the layout specs (`*.layout.spec.ts`, `pnpm dashboard:test:layout`, the unit-test builder's `layout` configuration: headless Chromium through `@vitest/browser-playwright`, touch through the DevTools protocol, installed by `pnpm dashboard:browsers`) find overlapping or cut header controls at the sizes that broke, fields under 16 px on a touch screen, a notice over the collection's card, a phone slide that does not run, a button label that clips its descenders, a switch (`mat-slide-toggle`, sized and coloured once by `mat.slide-toggle-overrides` in `styles.scss`) larger than a settings switch, under 3:1 off or on in any theme or with a touch target under 44 px, and a settings pane that ends flush with its scroller's edge. The default test run leaves them out
- Touch basics are by design for every input and size, never by width: `styles.scss` (Touch) keeps the page from bouncing or reloading when pulled, drops the tap flash, and makes controls answer a tap at once, without text selection or a callout (a link that leaves the app, `target=_blank`, keeps its callout); `followTouchInput` (`utils/touch-input.ts`, started by `AppComponent`) also holds the passive `touchstart` listener that makes iOS show `:active`. The shell, the phone's bottom bar, the details, the dialogs (the confirmation's text scrolls, its actions stay), the notices and the focused skip link keep out of the screen's safe area (`env(safe-area-inset-*)`, `--dialog-max-width`, `--dialog-max-height`), which is 0 on the desktop. The text of every field people type in is at least 16 px where the pointer cannot hover (`ui.field-text($size)`), since iOS zooms the page into a field with smaller text as it takes focus and leaves it zoomed; pinch zoom stays. Notices keep clear of the bottom of the screen's other surfaces too (`--notices-bottom` in `styles.scss`): the phone's bottom bar, and the collection's pill or card, whose reach from the window's bottom `CollectionStatusComponent` sets as `--collection-status-clearance` while one shows, measured again as its size changes (`elementSize`: a font coming in rewraps it)

## Script Rules

Use the namespaced root scripts so intent is obvious:

- `pnpm api:*`
- `pnpm cli:*`
- `pnpm core:*`
- `pnpm desktop:*`
- `pnpm dashboard:*`
- `pnpm types:generate`, `pnpm types:check`
- `pnpm verify`

Avoid reintroducing vague root scripts like `start`, `build`, or `collect` when a scoped script is clearer.

## Verification Rule

Always run the repo verification gate before considering a change complete:

```bash
pnpm verify
```

If `pnpm verify` cannot be run in the current environment, say so explicitly in the final handoff.

## Change Rules

- Do not reintroduce the old TypeScript backend
- Do not create thin migration or compatibility files when the code can be migrated directly
- Update docs when architecture, scripts, or workflow change
- Prefer deleting obsolete files over keeping dead compatibility layers
- Treat `desktop/gen/` as generated Tauri schema output: do not hand-edit it and keep it ignored
