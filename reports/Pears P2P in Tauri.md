# Tauri Can Host Hyperswarm; Networks Decide

Yes, the Holepunch stack can let a phone pair with the activity-log desktop app by QR code and read its data. There are two workable ways to run it on the desktop. The first ships Bare as a Tauri sidecar of about **42–46 MB**, driven over a framed stdin/stdout pipe. The second drops JavaScript entirely and uses the pure-Rust **peeroxide** port (v1.7.4, released 2026-11-03) in-process inside `core`. Embedding libbare or Bare Kit directly into the Tauri binary is technically possible but clashes with the cargo-xwin cross-build. The hard part is not Tauri. It is the network: HyperDHT is **UDP-only with no TCP or WebSocket fallback**, and holepunching **fails by design when both sides sit behind randomizing NATs**. Holepunch's own docs call such NATs "common on corporate and carrier-grade networks", which describes a desktop behind Cisco Umbrella talking to a phone on 4G. In that case you need a blind relay you operate. Even the "serverless" baseline also depends on three public bootstrap nodes that come with no SLA. On the phone side, Holepunch officially supports React Native/Expo with Bare Kit. Keeping the Angular UI instead means writing an unexampled Tauri-mobile or Capacitor plugin, or running peeroxide inside a Tauri mobile app (also unproven). The recommendation is to ship LAN-only QR pairing over HTTP first, at a cost of days, and to treat Hyperswarm as a gated proof of concept. That PoC starts with a one-day network probe on the actual corporate machine. If that probe fails, no amount of engineering rescues the serverless design. Claims marked _(inferred)_ are reasoning from the sources rather than stated in them, and effort figures are estimates.

## Bare ships cleanly as a 44 MB sidecar, not as an in-process library

### Five packaging routes, one that fits the cargo-xwin pipeline

Bare is Holepunch's small JavaScript runtime: V8 accessed through libjs, plus libuv. It has **Tier 1 prebuilds for Windows x64/arm64, macOS arm64/x64 (≥13), Linux x64/arm64 (glibc ≥2.35), iOS ≥15 and Android ≥10** ([Bare README](https://github.com/holepunchto/bare)). The prebuilt executables are distributed through npm as `bare-runtime-<platform>-<arch>`, not as GitHub release assets. Bare's own CI builds each OS on a native runner and never cross-compiles Windows from macOS ([prebuild.yml](https://github.com/holepunchto/bare/blob/main/.github/workflows/prebuild.yml)). That gap does not matter for a sidecar, because macOS can simply download the Windows `bare.exe` tarball and drop it into Tauri's `externalBin` _(inferred)_. Tauri requires each sidecar to carry a `-<target-triple>` suffix. Its documented rename script uses the host triple and "fails when cross-compiling", so the build should name `bare-x86_64-pc-windows-msvc.exe` explicitly ([Tauri sidecar docs](https://v2.tauri.app/develop/sidecar/)).

| Route                                | Desktop binary cost                                                    | Cross-build from macOS                                               | Signing                                                             | Verdict               |
| ------------------------------------ | ---------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------- |
| `bare-runtime` CLI as sidecar        | 46.2 MB win-x64 (17.4 MB gzip), 71.5 MB macOS arm64, 97.1 MB linux-x64 | Download prebuilt `.exe`; no compile                                 | Tauri signs sidecars; Windows cross-sign needs custom `signCommand` | Works                 |
| `bare-sidecar` stripped prebuild     | **41–44 MB** per platform                                              | Download prebuilt                                                    | Same                                                                | Best size             |
| `bare-build --standalone` single exe | Not measured                                                           | Accepts `--host`, untested from macOS _(inferred)_                   | Has own `--sign`, `--hardened-runtime` flags                        | Promising, unverified |
| libbare / Bare Kit linked into Tauri | Adds V8 to Tauri binary                                                | CMake + static V8 + whole-archive linking; untested under cargo-xwin | Single binary                                                       | High risk             |
| Node 26 SEA                          | ~100 MB `node.exe`, 147 MB macOS                                       | Plausible, undocumented                                              | Re-sign required                                                    | 2–3× larger           |

The sizes come from measured npm tarballs and Node v26.13.0 artifacts ([bare-runtime-win32-x64](https://registry.npmjs.org/bare-runtime-win32-x64/-/bare-runtime-win32-x64-1.36.0.tgz), [bare-sidecar 0.5.14](https://registry.npmjs.org/bare-sidecar/-/bare-sidecar-0.5.14.tgz), [nodejs.org/dist/v26.13.0](https://nodejs.org/dist/v26.13.0/)). The P2P native addons add almost nothing: **sodium-native is about 0.8–1 MB and udx-native about 0.2–0.27 MB per platform**, and both ship `.bare` and `.node` prebuilds for every desktop and mobile target ([sodium-native](https://www.npmjs.com/package/sodium-native), [udx-native](https://www.npmjs.com/package/udx-native)). Adding a Bare sidecar therefore grows the NSIS installer by roughly 17–20 MB compressed _(inferred; NSIS LZMA output was not measured)_. The JS bundle produced by `bare-pack --host win32-x64`, which embeds addon prebuilds by default ([bare-pack](https://github.com/holepunchto/bare-pack)), ships as a Tauri resource.

Signing is mostly handled for you. On macOS, the Tauri bundler signs sidecars "inside out" before the `.app` ([tauri-bundler app.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs)). This step is required, because the npm `bare` binary is only ad-hoc signed. On Windows the bundler signs unsigned sidecars and the NSIS plugins ([bundle.rs](https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle.rs)). When cross-compiling from macOS, however, "you must use a custom sign command", for example relic with Azure Key Vault ([Tauri Windows signing](https://v2.tauri.app/distribute/sign/windows/)). Holepunch's macOS example uses the `allow-jit` entitlement ([bare-macos](https://github.com/holepunchto/bare-macos)), so the notarized sidecar almost certainly needs `com.apple.security.cs.allow-jit` under the hardened runtime _(inferred; not documented by Tauri)_.

In-process embedding is where the risk concentrates. The C API is small (`bare_setup`, `bare_load`, `bare_run`, `bare_poll`, `bare_teardown`). But static libbare "requires whole-archive linking, because Bare relies on constructor functions to register native addons", and the build pulls static V8 from Holepunch's chromium-prebuilds through CMake ([Bare README](https://github.com/holepunchto/bare), [libjs](https://github.com/holepunchto/libjs)). **No Rust crate wraps it.** The only public FFI example is a zero-star repo ([cues-mantle runtime.rs](https://github.com/healthscience/cues-mantle/blob/main/src/conduction/runtime.rs)). Bare Kit's worklet API fits a tokio host better, and its CI does test win32, darwin and linux ([bare-kit integrate.yml](https://github.com/holepunchto/bare-kit/blob/main/.github/workflows/integrate.yml)). It has two drawbacks: it publishes no binaries, and an uncaught exception in a worklet "abort[s] the whole host process by design" ([bare-kit README](https://github.com/holepunchto/bare-kit)). A P2P bug would then crash the dashboard, which is a strong argument for keeping Bare out of process.

### A framed stdio pipe is the right Rust↔Bare bridge

Holepunch's own pattern is a dedicated duplex byte stream exposed in JS as `Bare.IPC`, with framed RPC on top. `bare-sidecar` opens it as an extra pipe on fd 3 and exits the child when the pipe closes ([bare-sidecar runtime.js](https://github.com/holepunchto/bare-sidecar/blob/main/lib/runtime.js)). `bare-rpc` 1.4.0 supplies length-prefixed, librpc-compatible request/reply frames ([bare-rpc](https://github.com/holepunchto/bare-rpc)). Rust's `std::process::Command` cannot pass extra handles on Windows the way Node does through `lpReserved2` _(inferred)_. The robust choice is therefore stdin/stdout with a uint32 length prefix (`tokio_util::codec::LengthDelimitedCodec` on the Rust side, `framed-stream` on the Bare side), carrying JSON or bare-rpc frames. Stderr goes to `core::diagnostics`, and no code may `console.log` to stdout _(inferred)_. The child handle must be kept alive and shutdown handled explicitly, because orphaned Node sidecars after app exit are a known Tauri issue ([tauri#8689](https://github.com/tauri-apps/tauri/issues/8689)). No public Tauri + Bare or Tauri + Hyperswarm project exists. Holepunch's desktop path is Electron, and pear-runtime's "WebView" host is still "Coming Soon" ([pear-runtime](https://github.com/holepunchto/pear-runtime)). The integration would be novel but mechanically ordinary.

## A pure-Rust port makes the JS runtime optional, at a maturity cost

Three non-JS implementations appeared in 2026. Each one reverse-engineered the JS code, because HyperDHT has **no byte-level spec**, only two prose documents ([handshake.md](https://github.com/holepunchto/hyperdht/blob/main/docs/handshake.md), [holepunch.md](https://github.com/holepunchto/hyperdht/blob/main/docs/holepunch.md)).

| Implementation                                             | Scope                                                                                                          | Interop claim                                                                                                      | Maturity signals                                                                       | Licence        |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | -------------- |
| **peeroxide** 1.7.4 (Rightbracket)                         | Hyperswarm, HyperDHT, holepunch, Noise/secret-stream, Protomux, blind-relay, UDX; pure Rust, tokio, RustCrypto | "Node.js peers can discover and connect to Rust peers and vice versa"; golden fixtures + live public-network tests | Created 2026-04-25; 20 stars; one human author; CI on ubuntu only; no Windows binaries | MIT/Apache-2.0 |
| cowlicks/hyperswarm (`hyperdht` 0.1.1, `hyperswarm` 0.1.0) | dht-rpc, connect, listen, relayed connections                                                                  | Receives connections from JS hyperdht                                                                              | "Work in Progress / Unstable"; holepunch not listed as complete                        | MIT            |
| hyperdht-cpp + Rust bindgen                                | HyperDHT only, 4 holepunch strategies                                                                          | Wire-compatible with hyperdht **6.29.1**, "~93%" parity                                                            | Needs pinned libuv 1.51 + libsodium, vcpkg on Windows                                  | **LGPL-3.0**   |
| datrs `hypercore` / `hypercore-protocol`                   | Hypercore data layer                                                                                           | Targets LTS v10, not v11                                                                                           | Older, 357 stars                                                                       | MIT/Apache     |

Sources: [peeroxide README](https://github.com/Rightbracket/peeroxide), [TESTING.md](https://github.com/Rightbracket/peeroxide/blob/main/TESTING.md), [ci.yml](https://github.com/Rightbracket/peeroxide/blob/main/.github/workflows/ci.yml), [peeroxide-dht/src](https://github.com/Rightbracket/peeroxide/tree/main/peeroxide-dht/src), [cowlicks/hyperswarm](https://github.com/cowlicks/hyperswarm), [IMPLEMENTATION_STATUS.md](https://github.com/cowlicks/hyperswarm/blob/main/IMPLEMENTATION_STATUS.md), [hyperdht-cpp](https://github.com/jjacke13/hyperdht-cpp), [datrs/hypercore](https://github.com/datrs/hypercore).

Only peeroxide genuinely makes the JS runtime unnecessary on the desktop. It covers the full connection stack and has no C dependencies, so it should compile under cargo-xwin like any other crate _(inferred; Windows is untested upstream)_. It would live in `core` behind the same Tauri commands the app already exposes. It carries three risks. The first is a single maintainer with a six-month track record. The second is that compatibility means "whatever JS hyperdht does", and that target moved from 6.29.1 to 6.35.1 in the same period ([hyperdht](https://github.com/holepunchto/hyperdht)). The third is that peeroxide does not appear to port `blind-pairing`, so pairing would be built from connect-by-key plus an app-level secret _(inferred from its module list)_. Binding the C libudx directly is pointless, because holepunching and NAT logic live in JS HyperDHT above UDX (`holepuncher.js`, `nat.js`) ([hyperdht/lib](https://github.com/holepunchto/hyperdht/tree/main/lib)). The Tauri webview cannot run Hyperswarm itself either. WebView2 and WKWebView expose no UDP, and the browser Direct Sockets API is limited to Chrome Isolated Web Apps ([Chrome Direct Sockets](https://developer.chrome.com/docs/iwa/direct-sockets)).

## The phone needs a native host, and only Tauri or Capacitor keep Angular

A phone browser cannot join HyperDHT. The official bridge, `@hyperswarm/dht-relay`, needs a server you host. Its repository is **archived**, its README says "Do not use it in production", and open PRs report it broken on hyperswarm ≥4.11 ([dht-relay](https://github.com/holepunchto/hyperswarm-dht-relay), [PR #29](https://github.com/holepunchto/hyperswarm-dht-relay/pull/29)). Its working "custodial" mode sends the client's 64-byte secret key to the relay ([protocol](https://github.com/holepunchto/hyperswarm-dht-relay#protocol)). Browser access is therefore off the table for a P2P design. The phone needs an installed app with one of four hosts.

React Native or Expo is Holepunch's own first-class mobile path. `react-native-bare-kit` 0.17.1 is a TurboModule exposing `Worklet` and `IPC`. `expo-bare-kit` 0.2.0 packs workers at Metro build time and requires prebuild or dev builds ([react-native-bare-kit](https://github.com/holepunchto/react-native-bare-kit), [expo-bare-kit](https://github.com/holepunchto/expo-bare-kit)). It cannot reuse Angular components except by wrapping the Angular build in a webview with a postMessage hop _(inferred)_.

A Tauri 2 mobile plugin wrapping Bare Kit is plausible because the pieces now match. Tauri mobile plugins are Swift packages and Kotlin Gradle modules ([Tauri mobile plugins](https://v2.tauri.app/develop/plugins/develop-mobile/)), and Bare Kit ships as an SPM package (`bare-kit-swift` 2.0.0) and a JitPack artifact (`bare-kit-kotlin` 0.2.0) ([bare-kit-swift](https://github.com/holepunchto/bare-kit-swift), [bare-kit-kotlin](https://github.com/holepunchto/bare-kit-kotlin)). The cost is glue code that no Holepunch example covers. Capacitor needs the same custom plugin and is closer to Angular's ecosystem ([Capacitor custom iOS code](https://capacitorjs.com/docs/ios/custom-code)).

The fourth option, a Tauri mobile app running peeroxide in Rust, avoids Bare on the phone entirely and with it the iOS V8 requirements described next. It is the least documented of all: nobody has published peeroxide on iOS or Android _(inferred)_.

Every Bare-based phone build inherits platform constraints. iOS runs V8 **jitless**, and apps must carry the `com.apple.developer.kernel.extended-virtual-addressing` entitlement for V8's pointer-compression cage ([chromium-prebuilds](https://github.com/holepunchto/chromium-prebuilds)). Android requires API 29 or later. The `BareKit.xcframework.zip` alone is 55 MB compressed across slices ([bare-kit-swift v2.0.0](https://github.com/holepunchto/bare-kit-swift/releases/tag/v2.0.0)). Churn is severe. bare-kit v3.0.0 reworked itself into a plain C library on 2026-10-30, moving the Swift and Kotlin bindings into new repos created days earlier ([bare-kit v3.0.0](https://github.com/holepunchto/bare-kit/releases/tag/v3.0.0)). Kotlin typed-RPC codegen is still "following" ([Pear docs](https://docs.pears.com/explanation/bare-on-native/)).

Neither OS keeps a P2P socket alive in the background. Android Doze "suspends network access" ([Android Doze](https://developer.android.com/training/monitoring-device-state/doze-standby)), and Apple restricts background services to listed purposes ([App Store 2.5.4](https://developer.apple.com/app-store/review/guidelines/)). The realistic UX is to open the app, reconnect, sync and cache. Same-Wi-Fi connections trigger the iOS Local Network prompt, so `NSLocalNetworkUsageDescription` is required ([TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)).

Reusing the UI is cheaper than it looks, because the dashboard already isolates its transport. The abstract `ActivityBackendClient` has `HttpBackendClient` and `TauriBackendClient` implementations, chosen at runtime (observed in `dashboard/src/app/services/backend/backend-client.ts`). A phone-side Tauri app could implement `get_activity` and `get_providers` as commands that proxy over the P2P stream, so `TauriBackendClient` would run unchanged. Write operations such as `saveProviderConfig` and `export` would reuse the existing `DesktopOnlyBackendError` _(inferred design)_. Because the desktop crate links OS collectors, the phone should be a separate small Tauri target that shares the dashboard build rather than a mobile build of `desktop/` _(inferred)_. QR scanning is covered by the official `@tauri-apps/plugin-barcode-scanner` ([Tauri barcode scanner](https://v2.tauri.app/plugin/barcode-scanner/)).

## Holepunching is serverless until a corporate NAT or UDP block intervenes

### Connect-by-key beats blind-pairing for a single desktop

The simplest secure QR pairing encodes the desktop's 32-byte HyperDHT public key as a **52-character z-base32 string** ([hypercore-id-encoding](https://github.com/holepunchto/hypercore-id-encoding)), plus a short one-time secret. The phone calls `dht.connect(key)`, which yields an end-to-end Noise stream authenticated against that key. The desktop's `firewall(remotePublicKey, payload)` callback then rejects every key not on its persisted allow-list ([hyperdht README](https://github.com/holepunchto/hyperdht/blob/main/README.md), [hyperswarm README](https://github.com/holepunchto/hyperswarm/blob/main/README.md)). A leaked public key cannot impersonate the desktop, and the one-time secret, together with a confirmation prompt on the desktop, limits what a photographed QR exposes _(inferred)_.

`blind-pairing` offers signed one-time invites and can embed bootstrap-free `additionalNodes` ([blind-pairing](https://github.com/holepunchto/blind-pairing)). It is built around Autobase room keys, though. It polls every **7 minutes by default** with no expiry ([index.js](https://github.com/holepunchto/blind-pairing/blob/main/index.js), [blind-pairing-core](https://github.com/holepunchto/blind-pairing-core/blob/main/index.js)), and it has had no npm release since 2024-10-31. It adds weight without adding security this app needs.

### NAT classes decide the outcome, and corporate networks sit on the wrong side

HyperDHT classifies NATs as OPEN, CONSISTENT or RANDOM ([constants.js](https://github.com/holepunchto/hyperdht/blob/main/lib/constants.js)). When exactly one side randomizes, a birthday strategy takes over: 256 sockets on one side, and on the other **1,750 probes over about 35 seconds**. The server rate-limits these random punches to one per 20 s ([holepuncher.js](https://github.com/holepunchto/hyperdht/blob/main/lib/holepuncher.js), [hyperdht index.js](https://github.com/holepunchto/hyperdht/blob/main/index.js)). When both sides randomize, holepunching fails and the connection "must be relayed through a third peer" ([Pear docs: connect by key](https://docs.pears.com/howto/connect-two-peers-by-key-with-hyperdht.html)). IPv6 is unsupported: the 2018 issue is still open and the 2022 PR was closed unmerged ([issue #1](https://github.com/holepunchto/hyperdht/issues/1), [PR #101](https://github.com/holepunchto/hyperdht/pull/101)). Holepunch publishes no success rates. Generic UDP holepunching succeeds on about 82% of NATs in Ford et al. and about 72% in libp2p's DCUtR data ([Ford et al.](https://bford.info/pub/net/p2pnat-abs/), [ProbeLab](https://probelab.io/talks/libp2p-nat-hole-punching-success-rate/)). As late as October 2026, Keet itself has an open report of desktop–mobile connectivity that "never completes" ([issue #306](https://github.com/holepunchto/hyperdht/issues/306)). A phone on carrier CGNAT reaching a desktop on a randomizing corporate NAT is exactly the double-randomized failure case _(inferred)_.

### Relays exist, but someone has to run them

HyperDHT "does not do any relaying by default" ([Pear docs](https://docs.pears.com/howto/connect-two-peers-by-key-with-hyperdht.html)). Relaying is opt-in through `relayThrough` with the TURN-like `blind-relay` protocol ([connect.js](https://github.com/holepunchto/hyperdht/blob/main/lib/connect.js), [blind-relay](https://github.com/holepunchto/blind-relay)). Pear 3.4.0 added `pear blind-relay start` for that purpose ([Pear v3.4.0](https://github.com/holepunchto/pear/releases/tag/v3.4.0)). The docs say to run the relay on "a VPS or any always-on host", note that a relay on either peer's own network "defeats the purpose", and say it "stores nothing" ([Pear docs: blind relay](https://docs.pears.com/how-to/connect-to-peers/relay-connections-through-a-blind-relay/)). No public relay operated by Holepunch exists for third parties. The relay-server mode PR explicitly adds no relay discovery ([PR #255](https://github.com/holepunchto/hyperdht/pull/255)).

Bootstrap is a separate dependency. Every node joins through three hard-coded hosts at `node{1,2,3}.hyperdht.org:49737`, on Hetzner and DigitalOcean, "served on behalf of the commons" with no named operator or SLA ([hyperdht README](https://github.com/holepunchto/hyperdht/blob/main/README.md)). A private DHT is possible but needs at least one persistent public node, which is a server.

### Cisco Umbrella's DNS layer is survivable; a UDP block is fatal

Bootstrap entries embed suggested IPs "to avoid DNS calls", so DNS-layer blocking of `hyperdht.org` alone probably does not break bootstrap _(inferred)_ ([hyperdht README](https://github.com/holepunchto/hyperdht/blob/main/README.md)). The transport, however, has been UDX over UDP since 2022 ([PR #82](https://github.com/holepunchto/hyperdht/pull/82)). The relay path is UDP too ([blind-relay](https://github.com/holepunchto/blind-relay)). The "pluggable transports" issue has been open since 2018 ([hyperswarm issue #1](https://github.com/holepunchto/hyperswarm/issues/1)). If Umbrella SIG or the corporate firewall blocks arbitrary outbound UDP or the P2P category, the desktop cannot join the DHT at all, and no relay fixes that _(inferred)_.

| Scenario                                | Infrastructure required                                                | Truly serverless?                        |
| --------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------- |
| Same LAN, UDP allowed                   | Public bootstrap nodes (LAN shortcut races holepunch)                  | Nearly; depends on third-party bootstrap |
| Home router ↔ phone on 4G CGNAT         | Bootstrap; birthday punch up to ~35 s                                  | Nearly                                   |
| Corporate randomizing NAT ↔ phone on 4G | Bootstrap **plus a blind relay you run outside the corporate network** | No                                       |
| Corporate network blocks outbound UDP   | Nothing in this stack works                                            | Not applicable                           |

## Permissive licences, fast-moving code, no audit

Licensing is not a blocker. hyperdht, hyperswarm, dht-rpc and hypercore are MIT. Bare, bare-kit, udx-native, blind-pairing and blind-relay are Apache-2.0 ([npm registry](https://registry.npmjs.org/hyperdht), [bare](https://github.com/holepunchto/bare)). peeroxide is MIT/Apache-2.0. The one exception is hyperdht-cpp, whose **LGPL-3.0** would impose dynamic-linking obligations on a closed Windows installer ([hyperdht-cpp](https://github.com/jjacke13/hyperdht-cpp)).

Maintenance is intense. hyperdht shipped 6.35.1 on the research date, with 51 commits in 2026, and Pear releases about every two weeks. Holepunch is Tether- and Bitfinex-backed, and Keet runs the stack in production on desktop and mobile ([CoinDesk](https://www.coindesk.com/tech/2022/07/25/tether-bitfinex-hypercore-launch-encrypted-communications-protocol-holepunch/), [issue #306](https://github.com/holepunchto/hyperdht/issues/306)). Volatility is concentrated above the networking core. Pear 3.0.0 removed `pear run` ([Pear v3.0.0](https://github.com/holepunchto/pear/releases/tag/v3.0.0)). pear-runtime and pear-mobile both call themselves "MVP – EXPERIMENTAL" ([pear-mobile](https://github.com/holepunchto/pear-mobile)). bare-kit broke its API four days before this report. Relay behaviour has several open PRs. **No public security audit** of hyperdht, hyperswarm or blind-pairing was found, and none of those repos has a SECURITY.md ([GitHub search](https://github.com/search?q=org%3Aholepunchto+audit&type=issues)). The prudent dependency surface is hyperdht/hyperswarm (or peeroxide) only, never the Pear layer _(inferred)_.

## Ship LAN HTTP now, prove peeroxide next, keep Bare in reserve

### Three architectures compared

|                     | **A. Bare sidecar + JS stack**                                                                                                    | **B. peeroxide in-process**                                             | **C. LAN-only QR over HTTP**                                                           |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Desktop shape       | `bare.exe` sidecar + `.bundle` resource, framed stdio RPC from `core`/`desktop`                                                   | New `core` module, tokio task, Tauri commands                           | Small HTTP server in `desktop` reusing `core` (as `api` does with Rocket), token in QR |
| Installer delta     | +17–20 MB compressed _(inferred)_                                                                                                 | A few MB of Rust _(inferred)_                                           | Near zero                                                                              |
| cargo-xwin impact   | None (prebuilt exe), custom Windows `signCommand`, macOS JIT entitlement                                                          | None expected; Windows untested upstream                                | None                                                                                   |
| Protocol fidelity   | Reference implementation (Keet's)                                                                                                 | Port; interop must be proven per JS release                             | Not applicable                                                                         |
| Phone               | Bare Kit (RN/Expo official; Tauri/Capacitor plugin unexampled); same JS on both ends                                              | Tauri mobile + peeroxide (unproven) or Bare Kit JS (cross-impl interop) | **Any phone browser**, Angular served by desktop, `HttpBackendClient` unchanged        |
| Works off-LAN       | Yes, subject to NAT/UDP; relay for corporate                                                                                      | Same                                                                    | No                                                                                     |
| Repo fit            | Adds a JS runtime and second language for networking, close to the AGENTS.md rule "Do not reintroduce the old TypeScript backend" | Rust owns the contract, matches `core` architecture                     | Matches existing HTTP client path                                                      |
| Effort _(estimate)_ | 5–8 dev-weeks incl. phone app, plus ongoing churn tracking                                                                        | 3–6 dev-weeks incl. phone app, plus interop CI                          | **3–5 dev-days**                                                                       |

Option C is not free of caveats _(all inferred)_. Plain HTTP on a corporate LAN exposes activity data and the token to sniffing. A page served from `http://192.168.x.x` is not a secure context, so WebCrypto is unavailable for app-level encryption, and a pinned-cert or JS-crypto scheme would be needed for confidentiality. Corporate Wi-Fi often isolates clients or puts phones on a guest SSID, and Windows Firewall will prompt on the first inbound listener. Even so, C delivers the core user value (glance at today's activity from the phone at the desk) with no phone app, no app-store review and no third-party infrastructure.

Between the P2P options, B is the better bet for this repository _(inferred)_. It keeps networking in Rust, avoids a second runtime with its signing and entitlement work, and leaves the cargo-xwin pipeline untouched. If both ends run peeroxide, there are no cross-implementation interop questions in the product path. A remains the fallback if peeroxide fails interop or on Windows, because the JS stack is the reference implementation and Keet proves it in production.

## Conclusion

The question that decides this project is not whether Tauri can host Holepunch. It can, two ways. The question is whether the one corporate network that matters lets UDP out and maps it consistently. Holepunch markets serverlessness, but in practice the stack is server-light. It relies on bootstrap nodes run by someone else and, for the corporate-to-cellular path, on a relay you run yourself. That puts the "no server" goal and the "works from anywhere" goal in direct tension for this deployment. A one-day probe resolves the tension cheaply before any architecture is committed.

The more durable insight is that the dashboard's existing `ActivityBackendClient` seam makes the transport replaceable. LAN HTTP, a P2P-proxying Tauri mobile shell and a future relay all present the same read-only commands to the same Angular UI. That lets the team ship value now and defer the bet on a six-month-old Rust port or a fast-churning Bare Kit until the network probe says the bet is winnable.
