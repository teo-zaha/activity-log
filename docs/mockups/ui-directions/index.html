How the UI grows: three directions

Activity Log is growing from a read-only log of your own work into a tool that also searches and writes to Jira Data Center (then GitLab and Odoo), tracks time and later lets an agent prepare writes for you. These are three ways the UI could follow. All three share one write pattern: a per-connection allow list, a core-rendered preview and a confirm button that names the effect. Mockups are static, 1280×800 desktop screens with made-up data, drawn in the app's own tokens.

Recommendation

Build A as the backbone. Take two pieces from C now, and B's command bar later.

A (new sidebar views: Work items, Time, Review) matches the reviewed plan and ships one visible step per phase. It reuses the detail panel, the confirm-dialog pattern and the sidebar, and it is the lowest-risk path to phase 1a.

From C, take the calendar's time grammar: day totals in every Day and Week header, plus solid, hatched and dashed blocks for “happened”, “booked” and “draft”. Also take C's review cards, shown in A's Review view instead of a docked tray. They are cheap and they carry the agent requirements (provenance, a fresh preview, a visible audit) without the tray's layout cost.

B's command bar becomes phase 5 polish. Once the actions exist it only lists verbs and opens the same dialogs, so it costs little then. Building it first would mean building A's dialogs anyway.

Revisit C's docked tray only if the agent becomes something you supervise all day, so that reviewing beside the calendar matters more than calendar width.

The directions

A · Views grow

A Work group in the sidebar: Work items (search with the detail docked beside the list), Time (a weekly timesheet with attendance and suggestions for unlogged time) and Review (agent drafts). Writes start from the detail action bar or the view's buttons.

Pros
  • The plan's section 7 as written. Every phase adds one visible thing
  • Reuses the sidebar, detail panel, dialogs and settings panes
  • The Time view answers “what did I book this week?”
  • Search results never mix with the timeline
Cons
  • The sidebar grows. The phone bottom bar must be regrouped
  • Time lives in two places (Time view and calendar totals)
  • Reviewing a draft means leaving the calendar
UI effort ≈ 15–21 dev-daysRisk: low
Open mockup A

B · Command-centric

The views stay. A command bar (⌘K or the header field) searches work items and your activity together, runs verbs (log time, new ticket, check in) with the preview inside the bar, and sends requests to the agent.

Pros
  • Smallest change to the layout people know
  • Very fast for keyboard users
  • One entry point for remote and local search
Cons
  • Hard to discover. Needs buttons elsewhere anyway
  • Jira create forms don't fit a bar. A's dialogs get built too
  • No good home for a queue of agent drafts
  • Weak on phones. Heavy focus and accessibility work
UI effort ≈ 18–25 dev-daysRisk: medium
Open mockup B

C · Workspace with agent

The calendar becomes the time surface: day totals plus happened, booked and draft lanes in every column. A docked tray holds Inbox (prepared writes, the agent's audit), Items (search and detail) and Time (totals, check in, timers). The sidebar folds to the rail while the tray is open.

Pros
  • Best agent experience: review beside the evidence
  • Unlogged time is visible where the work happened
  • One Inbox for every prepared write
Cons
  • A new layout state. The week gets narrow at 1280 px
  • Dense calendar. Lanes need care on small screens
  • Built around an agent that isn't designed yet
  • Largest effort
UI effort ≈ 27–36 dev-daysRisk: medium–high
Open mockup C

Effort counts dashboard and Tauri UI work only, across phases 1a–2 plus the review surface. The backend follows the plan and is the same for all three. These are rough estimates, not measurements.

Recommended path, phase by phase

  1. 1a, read only: the Work items view with the docked detail, Open in Jira through a URL core builds, and the Access tab (search and read only, with the probe). Nothing else changes.
  2. 1b, first write: the shared confirm component and the New ticket dialog. Add “Create ticket from this…” on entries. Add Actions history next to Logs.
  3. 2, time: totals in Day and Week headers, hatched logged blocks, multi-select with the selection bar, the Log time dialog, then the Time view.
  4. 4 and 4b, Odoo: day-only time entries in header rows, the Present row, check in and out behind the same confirm.
  5. Agent (near-term): the Review view with C's cards, dashed draft blocks on the calendar, an agent row in the Access tab.
  6. 5, polish: ⌘K command bar over the same verbs, and saved searches.

What these mockups surfaced for the plan

Agent drafts can't be the plan's pending plans. Pending plans expire after 5 minutes and only the channel that prepared one can confirm it, so an Inbox can't hold them. The simple fix is a draft: a saved request plus where it came from. The desktop app prepares it again when the user opens it, as its own channel, which gives a fresh preview and confirm id. The audit then records “requested by agent, confirmed by desktop”. This replaces the open “cross-channel handoff” in section 3.
Allowed and granted are two facts. The UI has to show them separately: the user's choice versus what the token or Jira user can actually do. A toggle that is on can still be refused, as with TRANSITION_ISSUES in the mockup: Move to… stays disabled with that reason, while Assign to me works.
“Present” needs attendance in the dashboard. Day totals as “logged out of present” rely on Odoo attendance entries. Without them, the fallback is the span of tracked activity, which is less honest. The label should then say “of tracked span”.
Phone layouts also run inside the desktop app (narrow windows). So writes must work in the phone layout too, as full-height sheets, while the browser build hides every action.

Open questions

  1. Direction: A with C's calendar grammar and review cards (recommended), all of C, or B?
  2. Agent drafts: should they survive an app restart (saved to a file, an Inbox you come back to) or live only while the app runs? This decides whether drafts need storage and a format.
  3. Weekly timesheet: do you report time per item per week (then A's Time view belongs in phase 2), or are day totals in the calendar enough for now?
