# AGENTS.md

This file defines the working rules and architecture expectations for agents editing this repository.

## Overview

`activity-log` is split into a Rust backend workspace plus an Angular frontend:

- `core/`: shared Rust library with models, collectors, cache, merge logic, markdown export, and TypeScript generation
- `api/`: Rocket HTTP API
- `cli/`: Rust CLI package containing the user-facing collection binary and the TypeScript generator binary
- `dashboard/`: Angular application that consumes generated backend DTOs
- `desktop/`: Tauri desktop shell that wraps the Angular app and talks to Rust commands

The backend contract is owned by Rust. The frontend consumes generated DTOs and should not redefine backend models by hand.

## Project Architecture

### Rust workspace

- `core/src/model/`: shared models grouped by domain/source. The `activity_entry!` list in `model/activity/activity_entry/` defines `ActivityEntry` and its shared accessors. It is read by its wire `source`: an object is read as the kind it names, with that kind's fields, or refused (B38). Each entry struct's `source` is that kind's tag (`model/activity/source_tag.rs`, one macro for the zero-sized tags, the one file with several types), so a struct can only name its own kind; `timestamp` is a `Timestamp` (`model/common/timestamp/`: the RFC 3339 text as the source wrote it, sent back unchanged, and the instant it names; text that names no instant makes none). Figma entries flatten `FigmaActivity`, a union of named versions, autosave checkpoints, comments and replies. Outlook and calendar entries flatten one `MeetingBody` (duration, busy status, weight, description, join link; `ActivityEntry::meeting`). What a source does not have is absent, never `""`, `"unknown"` or a placeholder (a Git commit's `branch`, a GitLab push's `title` and `targetType`, a meeting's `title`: the UI and the export show `(No title)`). `connection` is a `ConnectionName` (`model/activity/connection_name/`): unstamped in a collector's entry, stamped by `ProviderRuntime::collect` with a `ConnectionStamp` (never empty) before the day cache stores it; only a stamped name is serialized and only a non-empty one is read, so no entry is stored, sent or accepted without one. `core/src/model/activity/activity_entry/tests.rs` pins every kind's wire bytes
- `core/src/model/change_stack/`: `ChangeStack`, where a change (a GitLab merge request or a GitHub pull request) stands among its repository's open changes as the host has it now, not on the entry's day: one wire type every code host's entries carry (`GitLabEntry.changeStack` and `PullRequestRef.changeStack`), its parts one per file. It holds the change itself (`current`), what it builds on (`below`, from the base up), a typed `bottom` (`reached` with its branch, `ambiguous`, or `cut`) and the tree `above`, whose every level ends `complete` or `cut` (`StackCut`: `limit`, `unreadable`, `throttled`, `failed`, `cycle`). Made only by `ChangeStack::new`, which reading one runs too (`try_from`): more than its change alone, no blank title or branch, `http(s)` links without user info, no change twice on one path. Absent when the change is not open, stacks with nothing, or its openness could not be told
- `core/src/collect/`: one collector per source, and what several share: `meeting_text/` (a meeting description's readable text and its join link, for the calendar feed and Outlook), `change_stack/`, and `web_link/` (validates links against their web origin, with `Unshown::Elsewhere` carrying the unexpected origin or `NotAWebPage`)
- `core/src/collect/calendar/feed/`: startup and collection share one network request path. For a non-busy HTTP 401, 403 or 404, the typed `FeedUnavailable` holds a `RemoteFailure` and the service recognized from the original HTTPS host on its default port without user info. Redirects preserve that service and send no referrer. The Calendar client refuses every HTTPS-to-HTTP redirect hop with a host-only typed error and uses the normal redirect limit for allowed hops. The startup check shows `failed` and a running collection shows `collectionFailed` for a refused downgrade. Diagnostics keep only the original host and the safe HTTP failure. The configured feed URL is a secret.
- `core/src/collect/figma/`: collects the verified Figma principal's versions, autosave checkpoints, comments and replies from pasted links or keys, desktop tabs, and configured team folders. A recent UTC chunk reuses a complete folder tree for 24 hours and lists each folder's files once per run. Older chunks discover missing teams. A failed or paged listing preserves the old tree. A team sighting selects a file when its saved modification is at or after the chunk's start. An eligible tab record also selects the file. Removing a team immediately stops its sightings from selecting files. The first stale chunk lazily reads the shared tab snapshot through bounded, non-following owner-checked file I/O. Each connection filters it by its own account. A private `.files.json` book beside the day cache remembers discovered keys by connection and identity across config edits. Each chunk re-reads the book under its lock, saves new sightings before fetching and records contributions before handing entries to the day cache. It prunes files only after 60 days without either a sighting or a contribution. It reads at most three files at once and sorts each file's entries by instant and id. A failed request for a pasted file or configured team's listing fails the range and names its position. A discovered file confirmed lost is skipped, counted and retried at most daily or when a tab reappears after being absent from the previous snapshot. Other failures fail the chunk. Ambiguous file and team 403 responses share one account probe per run. Replies use their root comment's node for links.
- `core/src/collect/change_stack/`: change stacks whatever the code host, with no host's code in it: which open changes a change builds on and which build on it, by the branches they come from and go into. A host implements `ChangeLookup<R>` over its repository key (GitLab's project id or GitHub's owner/name; `open_page`, `open_numbers`, `open_from`, `open_into`, `concurrency`), and `change_stacks` does the rest for one connection. `lookup/`: the trait, `OpenChange`, `OpenPage` (`Complete` or `Partial`) and `LookupFailure` (a `FailureKind`: `Unreadable`, `TokenInvalid`, `ScopeMissing`, `Throttled`, `Limit` or `Failed`, with its typed `LookupCause`: the request's `ApiError`, a repeated page or an ignored filter). `budget/`: one connection's `Budget` for one collection, `STACK_REQUESTS` (50) reserved atomically before each request and the `STACK_BUDGET` deadline (20 s), past which a lookup is `Limit`; its breaker, tripped by a refused token, a missing scope or a busy host, refuses every later request with that reason. `Budget::phase` gives a lookup phase its own request allowance and a deadline capped by its parent's. It shares the parent's breaker. `walk/`: a repository's first page answers every walk there from memory when it holds all its open changes; otherwise openness is asked by number and each branch question once (a single-flight memo, failures included). `change_stacks_with_seeds` accepts pre-resolved `StackSeed`s (current change, known members, base branch and whether more changes lie above) and extends below from that base and above from the known top, cutting the top at `limit` when incomplete. `UnreadChanges` carries pre-walk failures into the summary. The summary counts unknown changes and counts each affected repository once per failure kind. Below is walked down to the base (`ambiguous` where several open changes come from one branch), above breadth-first, children by number; `STACK_DEPTH` (12) per direction and `STACK_MEMBERS` (30) per stack end it with `limit`, a change already on its path with `cycle`, a failed lookup with its cut (a refused token or scope shows as `unreadable`); a change whose walk never started is `cut{limit}` both ways, never shown as not stacked. Changes are walked newest event first, so the result depends on no map's or server's order. It all runs inside the caller's future (no task is spawned), so dropping it stops every request; one summary line per connection, and one warning per kind of failure with its counts and first cause
- `core/src/lib.rs`: orchestration entry point used by both `api` and `cli`; numbers ids a source repeats (`id#2`), so `(source, connection, id)` names one entry (the runtime stamped `connection`). `collect_connection` runs one connection's collection under `COLLECT_TIMEOUT` (120 s), logs it (`Collected N entries in … ms`), and then, after the day cache and outside that timeout, its `annotate` step (`ProviderRuntime::annotate`) under `ANNOTATE_TIMEOUT` (`STACK_BUDGET` + 2 s), a safety net for an adapter that overruns its own deadline: entries are only lent to it, so none is lost when it is stopped, and what it adds (change stacks and project details) is never cached and reaches days the cache served too. The connection settles only after it, so a GitLab connection with project events or a GitHub connection with pull request events can stay `pending` up to about 22 s longer than its collection took (the CLI waits as long)
- `core/src/aggregator/`: builds an `ActivityLog` from per-connection results: pairs each host’s events for a full SHA with local Git rows in connection and repository order. `HostedCommit` supplies the SHA, source and order key (instant, `ConnectionId`, id). GitLab supplies pushes with `pushedCommit` and GitHub supplies `committed` actions. A Git row can carry both optional host fields and still counts as one fold. Unpaired host events stay entries. The projection sorts, counts, and shows what pending connections carry (`carried_for`, without a commit a finished connection has)
- `core/src/runtime/`: `Host` (`runtime/host/`), the collection state shared by `api` and `desktop`, one per process: the installed config's connections and their checks, the collection on screen, config edits (`Host::edit`, through `settings::edit_config`) and reloads (`reload_if_changed`, by content id; `watch_config` looks every 2 s and installs a change another writer made once it read the same twice 200 ms apart; a file that does not parse is logged once and the last good config stays), and the published state (`subscribe`: a `watch` of `Published`: the host's `epoch`, the `authority` that each config install and each collection key a check replaces (`KeyChange::Replaced`: another account than entries may be shown for; a first answer after an install is `First` and no boundary) raise and stamp both parts with, so the checked provider and the eviction of the old account's entries reach a subscriber as one pair, and activity and providers with a host-wide revision per part; `runtime_state` reads it as one `RuntimeState`, both parts of one moment; `feed` gives one subscriber a `Feed`: the current value, then the latest after each change, values in between skipped, until shutdown). `runtime/forward/`: what a subscriber of the feed is sent (`docs/plans/shared-contracts.md` §5): a `Forwarder` per subscriber makes a `state` pair due first, after an authority it was not sent and after `reset` (a failed delivery), and otherwise each part whose revision rose (`Due`); each accepted message is acknowledged on its own; `take` hands everything due in revision order; `RuntimeMessage` is the event name and its DTO's compact JSON, `ping` (`RuntimePing`, the host's epoch) included, which no forwarder makes due. The SSE route and the desktop's events both use it. Every transition is decided, installed and published under one short state lock; a run or a check that is no longer current changes nothing (run ids and check generations are host-wide). Work goes to the adapter's `RunSpawner` only after the lock is released, so each command answers with the state it installed and that part's `PartStamp` (`Answered`: `collect` running, `recheck` checking; an edit's new connections checking with its `InstallReceipt`, `None` when the file was written but the host shut down before it installed it (B70): the save is durable, no revision shows it); a run's work resolves to its `RunEnd` once its end shows (`is_current` tells whether it still does), a check's to `None`. `collect`: a running collection of the same range goes on, another range replaces it. `recheck` runs one connection's check again and collects its kind again for the range on screen (a running collection starts over, a failed one runs whole). An install collects again only the kinds it affects (`affected_kinds`: a connection added, removed, reordered, with other values, location or table `instance` (removed and added again; a legacy table's first instance is no change), or with no outcome yet); a running or failed collection runs whole, and a label edit still collects a kind whose fresh check finds another account. A check is recorded before any collection uses it. A recorded key change also clears that connection's failure. A collection can prove the account was refused or changed. While applying either a progress or final report, `record_collection_denial` validates the current run and planned key, records the connection unavailable, advances the key and publishes the eviction and refusal together. Only `KeyChange::Replaced` raises authority. Repeated reports under the old key cannot repeat the transition. Resource refusals, missing scope, throttling, timeouts, unreachable endpoints and typed remote decode failures keep same-key entries and show the collection failure as degraded. Nothing is logged under the state lock: a transition's lines are emitted after it is released (tests assert it). `shutdown` is the last transition: the shown run stops, runs and checks still in flight are no longer current (a run ends `Stopped`, a check publishes nothing, `is_current` is false), and no edit or reload installs anything; the spawner is dropped, and the config watcher and every feed end. `runtime/report/`: what a run reports per connection (`RunReport`, `Slot`, `Outcome`, `Stored`; a failed connection's `CollectFailure`: its `ClassifiedProblem` from `source_failure::problem_of` or the collection's timeout—telling `timedOut`, `refused`, `scopeMissing`, `feedUnavailable`, `throttled`, `unreachable` and local/store causes apart from `collectionFailed`—its message, and any typed identity evidence from `source_failure::collection_identity_of`) and the `Collector` that produces it (`collect_planned` in production; a run does not fail as a whole: only a panic ends one failed); `runtime/result_store/`: the shown run's report, from which the log is folded (`RunReport::project`) and the next run's plan is taken (carry, keep); `runtime/keys/`: each connection's `CollectionKey` (values, location and the identity its check found: `Verified` or `Denied`; an inconclusive answer keeps the previous key), so entries collected under one key are never carried, kept or shown under another. A connection whose last collection failed is listed `degraded` with its failure's problem and the error as its reason; a label edit keeps that
- `core/src/provider/`: one adapter per source kind (`provider!` declarations: supported OS, typed config, which the startup check gets resolved, cache policy, startup check, collect, and optionally `annotate`: what is true now rather than on the entries' days, added to one connection's collected entries, infallible, fields only, written in one pass after every await; `provider::adapter(source)` and `provider_registry()`, built once, in `Source` order), the per-connection `ProviderRuntime` and the typed startup problem (`ProviderInfo.problem`; a check ends in a `CheckOutcome`, `Available`, `Degraded` or `Unavailable` with its `ClassifiedProblem` and reason, which `CheckOutcome::apply_to` writes into `ProviderInfo` together with `usable` and `recheckable`: any problem but `unsupported` can be checked again; a refusal of the credentials is `refused`, a confirmed missing permission is `scopeMissing`, an unavailable feed is `feedUnavailable`, a busy server is `throttled`, and a server out of reach is `unreachable`; `provider/source_failure/`: `ClassifiedProblem` keeps a plain problem or a typed `FixCause` (`AutomationDenied`, `FolderDenied`, `AppNotRunning`, `FeedUnavailable`), and `problem_of` reads it from the typed causes in an error's chain—`FeedUnavailable`, `RemoteFailure`, `JiraResponseError::Anonymous`, `SourceFailure` (`SourceProblem`: `notInstalled`, `notRunning`, `permissionDenied`, `noData`), `secrets::StoreError`, `OutlookNotRunning` and an `AppleScriptError`'s number—for `ProviderCheckResult::unavailable_from` and `CollectFailure::of`)
- `core/src/provider/fix_action/`: selects the optional `ProviderInfo.fixAction` once, after the host applies any collection failure to the provider health. The API host uses the web surface, which omits native targets. The macOS desktop surface can offer Automation settings after a typed Apple Events refusal for Outlook, Files & Folders for a local Git root denied with `EPERM`, and Outlook launch. The source error carries manual guidance across the CLI, web and desktop. Each token provider declares its `CredentialSetup` beside its config. The health projection for `refused` and `scopeMissing`, saved token fields and valid draft addresses share that declaration for setup links and permission wording. Credential URLs use the validated configured web origin (with the Jira and GitLab context paths), or Figma’s fixed settings URL, with fixed encoded parameters. The runtime-message decoder and Tauri settings response guards validate the optional actions and their nested fields before the dashboard can use them. The Calendar adapter declares static `feedHelp` on its secret field through `field_help`. The same guide catalog supplies recovery for a typed `FeedUnavailable` on web and desktop.
- `core/src/provider/{jira,gitlab}/api/`: `JiraApi` and `GitLabApi`, the only way the Jira and GitLab checks and collectors reach their servers (`remote_api/` holds the shared client). Paths are built from segments and query values through `query_pairs_mut`, never with `format!`; credentials go only to the configured origin (a redirect elsewhere stops, a URL with a user name or password leaves the connection not configured). The shared HTTP client sends `activity-log/<version>` as its user agent. Every remote failure goes through `remote_error/` (`ApiError`, `remote_message`: the server's own message only, secrets redacted, addresses without user info or query, control characters escaped, at most 300 characters; error bodies are read only in part, with Figma's `err` treated as an explanation). JSON POSTs share the GET request path. GraphQL refusals keep typed codes and paths in `QueryRefusal`, with messages redacted. The ordinary response path fails on any error. A provider with a specific partial-answer policy can inspect the typed refusal and data together on `QueryAnswer`. `ApiError::problem` and the retry decision share one rule for a busy server. It answers with 429, 503 with a readable `Retry-After`, 403 with a readable `Retry-After` or `X-RateLimit-Remaining: 0`, or a GraphQL `RATE_LIMITED` error. A busy response takes precedence over a confirmed OAuth or GraphQL scope error. A busy check is unavailable with `throttled` and leaves the account key as it was. A busy collection shows as degraded with `throttled`. After the busy check, a 401 or 403 with `insufficient_scope` or a GraphQL `INSUFFICIENT_SCOPES` error is `scopeMissing` and adds no identity evidence; other non-busy 401 and 403 responses or a GraphQL `FORBIDDEN` error are `refused`. An error answer's RFC 6750 code (`OAuthRefusal`: `invalid_token`, `insufficient_scope`, `invalid_request`, from `WWW-Authenticate: Bearer` or the body's `error`) is kept on `ApiError::Status` for callers that tell a refused token from a missing scope; a body that breaks off is a transfer failure, never an unreadable answer. The startup check parses its identity request (Jira `/myself`, GitLab `/user`) into `IdentityEvidence`, which the runtime records on `ProviderContext` for collection and annotation to read through `identity()`. For GitLab this names the token owner, while the configured user determines whose events are collected. The shared identity check reports `failed` with no identity evidence or setup action when the API responds successfully without a usable account ID. The connection is unavailable and the runtime preserves its collection key. A JSON response with `X-AUSERNAME: anonymous` raises the typed Jira refusal on `/myself` and search. Jira startup checks also require a usable account `key`. A successful Jira response without one is `refused` and shows the credential link. These two startup cases carry no identity evidence. Search requires `issues`, which may be empty. A missing header leaves the JSON subject to the same rules. `RemoteClient` retries a busy answer as its caller's `Retry` says: `OnceShort` (once, when the server asks to wait at most 10 s and the wait fits before any startup check deadline. A retried check that runs out of time reports its first busy answer) or `Never` (the change stack lookup, which stops at the first). `provider/gitlab/api/pager/`: GitLab's paged lists (`Pager`), shared by the collector and the lookup: each page is paid for with a `RequestBudget` before it is sent (`Unmetered` for a collection), and `remote_api::paging::PageGuard` stops a list that repeats a position or returns only rows already read (`PageError::Repeated` in GitLab); `api/merge_requests/`: a project's open merge requests by a `MergeRequestFilter` (all, numbers, from or into a branch; never empty or blank, which GitLab would read as no filter), each row checked against the question (`RowFit`)
- `core/src/provider/github/` and `core/src/collect/github/`: GitHub seals the token for the configured web origin and derives and pins its REST and GraphQL endpoints ([ADR 0007](docs/adr/0007-github-api-origin.md)). Startup checks the token owner with `/user`. GraphQL reads the viewer’s opened pull requests and issues and submitted reviews in windows of up to 364 days. The collector walks the viewer’s own pull requests by update time and reads every review in range. Inline comments use their review's submission time, and only in-range reviews page their comments. Conversation comments use their own creation time. The collector walks them by descending update time with one cursor per connection across cache chunks, skips node-scoped access refusals when the rest of the page is readable, and warns once per connection collection. GitHub stores trimmed plain `bodyText`, while GitLab stores its Markdown source. Blank bodies are absent. PR comment targets participate in annotation with the same 50-request stack budget as the other PR entries. It finds merges and closes with one aliased date-qualified search, checks the viewer ID against the recorded actor, and keeps all in-range close events from each candidate. Each window of at most 364 days allows 24 search requests total, with up to ten 100-row pages per query and date splits at 1,000 results. Close timelines allow five 20-row pages per item and 24 continuation requests per window. It warns when results reach an unsplittable search cap or a request limit leaves pages unread. Searches sort by creation time and skip node-scoped `FORBIDDEN` in readable pages. One warning per connection collection counts refused search results by appearance. Searches miss actions outside their involvement and review qualifiers. A settled day refreshed after its TTL can lose a close found in the original chunk if the item was re-closed later in that chunk. For commits it discovers contributed repositories, splits truncated lists that hit the query cap, warns if a shorter list omits repositories GitHub counted, then reads default-branch history with Contents read permission and the viewer’s node ID. GitHub’s history policy for static `nodes` batches and `node` continuations skips a requested repository for `FORBIDDEN` or `NOT_FOUND` at its root or below. Commit rows use `committedDate` and optional origin-checked URLs. Live checks remain open for the history date filter, discovery totals and refusal paths. `PullRequestRef` and `IssueRef` carry optional `webUrl` checked against the configured web origin. A trailing DNS dot is equivalent for links. Settled cache days stay fresh for 30 days.
- `core/src/collect/github/releases.rs` reads published releases from the repositories found by commit contributions in the same window. The release node ID names the entry, `publishedAt` dates it, and the typed `prerelease` flag preserves prereleases. GitHub exposes the release author as the attribution source, which can differ from the account that publishes a draft. Discovery can miss release-only repositories, and stopping by creation time can miss a draft created before the window and published inside it beyond the scanned pages. The existing commit-history query reads the first release pages through a separate `releaseNodes` alias for repositories without pages in the collection memo. Batches hold up to 20 repositories and each page reads `RELEASES_PER_PAGE` (100) releases. Continuations are batched, guarded by `PageGuard`, and reuse pages across cache chunks. Each window includes pages through the first whose oldest readable creation date is before its start, with `RELEASE_PAGES_PER_REPOSITORY` (3, including the first page) and `RELEASE_CONTINUATION_REQUESTS_PER_WINDOW` (24). The collection warns once with the number of repositories cut off by a cap or a page with no readable rows. Scoped refusals are counted. A refused continuation preserves earlier pages for that repository. Links use the GitHub web-origin rule. Releases use neither commit folding nor change-stack requests.
- `core/src/provider/figma/`: `FigmaApi` uses `RemoteClient` at `https://api.figma.com` with `X-Figma-Token`. Its `/v1/me` check supplies the principal used for filtering and caching. The PAT binds to the kind because the API has a fixed origin. `FigmaScope` parses and deduplicates optional `FIGMA_FILES` and `FIGMA_TEAMS` lists. Collection logs the number of duplicate items ignored in each list. With both lists empty, the verified account needs a matching tab or live tab-discovered record. Configured teams require `folders:read`. `FigmaFileKey` reads file and branch keys from links and tab paths, and `FigmaTeamId` reads team links and numeric team IDs. V2 folder and file listings reject paged responses (`FolderListingError::Paginated`). Version paging sends its own `before` cursor and uses the shared `PageGuard`.
- `core/src/provider/gitlab/annotation/`: adds the current `project` (path with namespace) and optional `webUrl` to GitLab events after the day cache. It asks once per project, newest event first with ties by project ID, four at a time. Projects have 20 requests and up to 5 s. Stacks keep their 50 requests and the remaining time. Both phases share the 20 s annotation deadline and the breaker. A failed lookup leaves the fields absent, with grouped typed failures logged. URLs are built from an origin-checked project page and the event's merge request or issue number. Project details and stacks are prepared before any entries are changed
- `core/src/provider/gitlab/stack/`: GitLab's side of change stacks, `GitLabChanges` (`ChangeLookup<u64>` over `GitLabApi`, 4 requests at once, numbers 50 per request) and `look_up`, which finds the stack of every merge request event's change (`projectId`, `mrIid`; never a push, which folds into a commit) for the annotation to write on each entry, clearing it where there is none. Requests are `Retry::Never`. A busy answer is `Throttled`, even when it carries an OAuth refusal code. For other answers, the OAuth code decides first (`invalid_token`, `insufficient_scope`; `invalid_request` is `Failed`), then the status (401 a refused token, 403 and 404 a project hidden from it). A row of another project, number or branch fails its list (the filter was ignored); one no longer open (`locked` while it merges) is left out and counted in one line. A link to another origin than the configured URL's is dropped and counted, and one warning per collection names the count and the origin GitLab linked to (scheme, host and port)
- `core/src/provider/github/stack/`: looks up native pull-request membership by alias (50 per request) before using the shared branch walk for open pull requests with no native stack or an older schema that refuses `stackEntry` with `undefinedField`. Native positions seed `change_stacks_with_seeds`, which continues from the native base branch and the top pull request’s head branch within the same limits. Both lookup paths reserve from one connection budget and use `Retry::Never`. Batches after the initial native probe use up to four concurrent requests. HTTP 401 and 403 stop the connection’s requests unless typed evidence gives a different classification. A bare HTTP 404 is a request failure. Repository access refusals use GraphQL error codes. A malformed alias is counted and the other aliases are read. The branch walk reads open pull requests and checks the repository, number and branch filters. The GitHub API's `pager/` is shared by the collector and the walk. Annotation fills each pull-request reference outside the day cache (skipping `Merged` entries, while `Closed` PRs still check stacks in case they were reopened). Links pass the configured web-origin check.
- `core/src/platform/`: OS integrations shared by collectors (Windows COM/event log, macOS AppleScript run in its own `osascript` process, so a timeout or a stopped collection kills it); `platform/dirs` holds the OS settings and cache folders; `platform/blocking` runs blocking OS work (Git walks, `wsl.exe`, Outlook COM, the event log) on a thread with a flag set once nobody waits, so it stops and kills the process tree it started (a process group, a job object on Windows), and lets one job at a time reach each resource; work that stops so ends with the `Stopped` error, told apart by its type (`err.is::<Stopped>()`); `platform/private_file/` writes files only the current user can open (settings, the cache): `Folder::replace` writes a file created private inside a verified owner-only staging folder beside the target, flushes it and moves it over the target through folder handles (on Windows `NtSetInformationFile`'s rename relative to the parent's handle, since the Win32 `SetFileInformationByHandle` refuses a `RootDirectory`), and a failure names its step (`ReplaceError::Failed` with its `ReplaceStep`) and leaves the target as it was. `Folder::read_owner_only` reads a file only if, judged on the handle it is read through, it is a regular file of the user's no other account may read or write (`OwnerOnly::Private` or `Exposed`). Names are single entries of a folder, on Windows also ones Win32 and NT read alike (no trailing dot or space, no device name such as `CON` or `COM1`). A location that cannot keep files private (FAT, exFAT, network shares, a folder other accounts can write to) is `Unprotectable` before anything is written. Its OS modules are chosen with a compile-time `imp` alias. `platform/secret_store/` is the one item of the OS secure store that holds the config key (`docs/adr/0006-secure-secrets.md`): a generic password created in the default keychain and read through the search list on macOS, every keychain call under one process-wide lock (`Interaction::Never` turns dialogs off for the whole process), the credential `activity-log/config-key` (`CRED_PERSIST_LOCAL_MACHINE`) on Windows, an item of the Secret Service's default collection through `oo7::dbus` on Linux (each call 5 s at most; an empty search of a collection still locked is `Refused`, never absent; only a missing bus or service while connecting is `Unavailable`), a `fallback` that is `Unavailable`; each answer is definite (`Absent` only for a store that answered and holds none) and the status tables are pure functions tested on every host. `platform::parsed_output_command` starts a subprocess whose output is parsed in the C locale (`last`, `pmset`, `osascript`, git's `user.email` fallback); the WSL script exports `LC_ALL=C` itself, since `wsl.exe` passes no environment in
- `core/src/secrets/`: the config key and its stores. `SecretStore` (`read` with an `Interaction`, `probe`, and `creator`, the `KeyCreator` whose `create_if_absent` only a store this program may create the key in offers; a `Lookup` or a `StoreError` of kind `Unavailable`, `Refused` or `Failed`) is implemented by `OsStore` (over `platform/secret_store`), `KeyFileStore` (`secret.key` in the local data folder or `ACTIVITY_LOG_SECRET_KEY_FILE`, written owner-only through `Folder::replace` and read through `Folder::read_owner_only`; `KeyFileAccess::ReadOnly` for the desktop and the API, which have no creator) and, under the `test-support` feature, `MemoryStore` (scripted answers, call counts, held reads). `Secrets` is the handle a binary builds once (`Secrets::desktop`, `::cli`, `::api`, `cfg(not(test))`, so core's tests never reach the OS store; `with_stores` for tests): `key` is a reader's key, held once found, concurrent first readers sharing one read that runs as its own task, settled however it ends, and is waited for at most `KEY_WAIT` (120 s), a failure never kept and an attempt older than that asked again; `fresh_key` is a writer's, read again every time, and only its `Absent` gives a `KeyCreation` (`AbsentReadOnly` where the store has no creator), which creates under the key-creation lock (`secret-key.lock` in the OS config folder, on Windows the known Roaming AppData folder whatever `APPDATA` says; `secret.key.lock` beside the key file), reading once more, warning, storing, reading back and comparing. `DataKey` (64 bytes, zeroized, never printed). `secrets/sealed/`: format v1 (`docs/adr/0006-secure-secrets.md`), `seal` and `open` (AES-SIV, `Aes256Siv`, the associated data a vector: the format, the header, the field's wire name, the `Binding`), `SealedValue` (`parse`, strict; `Malformed` by part; `sealed_for`, the binding tag read from the file alone), `KeyId`, `BindingTag`, `Binding::of(source, values)` (the kind's `[binds]` keys in declaration order: a URL's origin with its port always written, only for an `http(s)` address without user info, as the remote client sends; the binding tag is a display hint, never what a save compares; five vectors cross-checked with OpenSSL's AES-SIV and RFC 5297's A.1 and A.2 pin the format and the crate. `aes`, `cmac` and `ctr` are core's own dependencies only to turn on their `zeroize` features. `secrets/opening/`: a connection's sealed secrets opened (`open_connection`: the store's key through `Secrets::key`, then `open` for the binding the table names now; `Opened::over` reads the values with the opened text in place) or why the first did not (`Unopened`: `NoKey`, `Unopenable`, `Unreadable(Malformed)`, a newer version's own case, `Unbound`, `Store`, which alone is `secretUnavailable`; the others `notConfigured`, with words for people in `reason`). `secrets/choice/`: the one rule of where a front end keeps the key (`Choice`: `FrontEnd`, the profile, `ForcedStore`, whether it has an OS store; `info` from the OS store's last answer, `OsAnswer`), which `SecretStoreInfo` shows: the desktop the OS store or nothing, the CLI and the API the OS store or, where there is none, the key file, the dev profile its key file. `ACTIVITY_LOG_SECRET_STORE` chooses where the key lives and configures no source (`os` takes the CLI's fallback away, `file` forces the key file in the CLI and the API; Tauri names a command by its function, so `desktop/src/tests.rs` invokes every name here and the menu's through the app's own handler (`app_commands!` in `desktop/src/lib.rs`) and checks it takes each
- `core/src/model/common/backend_error.rs`: `BackendError { kind, message }` (`message` sent as `error`), what every API error body is and every desktop command fails with; `kind` is the generated `BackendErrorKind` union (`noData`, `invalidRequest`, `notFound`, `alreadyExists`, `busy`, `conflict`, `noLocation`, `unprotectable`, `badConfig`, `tooLarge`, `secretStoreUnavailable`, `secretStoreRefused`, `internal`). `core/src/backend_error/` is the one place core's typed errors get their kind (`From` for `RangeError`, `ExportError`, `ConfigEditError`, `ConfigError`, `LoadError`, `EditError`); `runtime::answer_collect` and `runtime::answer_recheck` are the collect and recheck answers the API and the desktop both give
- `core/src/utils/`: `now_iso`, `stable_id` (FNV-1a) for entries whose source has no id, `random_u64`
- `core/src/cache/`: per-day disk cache for remote API providers. A provider opts in with `cache: CachePolicy::api()` in its `provider!` declaration; the runtime fetches only missing or stale days, in contiguous chunks of up to 92 UTC days by default, newest first. Jira uses `without_run_chunks` because its JQL has only a lower date bound. The API policy defaults to a 7-day settled TTL, and `api_with_settled_ttl` lets a provider keep settled days fresh for a different duration capped at the pruning age (60 days). A file holds each day's entries as they are sent, read by their `source` (version 7, GitLab entries with their `projectId`; a file of an older version is fetched again and replaced, one of a later version left alone). One file per connection and verified principal (`ProviderRuntime::cache_scope`: the safe fingerprint, URLs as their endpoint, plus the check's `RemoteIdentity`); without a verified identity, or with a query or fragment in a URL, the connection is collected uncached (a URL with a user name or password leaves the connection not configured, so it is not collected at all). A folder that fails `Folder::check_private` is neither read nor written. Each chunk is written as soon as it is fetched: without a lock during the fetch, then under `{file}.lock` re-read, merge only its days (newer `fetched_at` wins, ties keep the stored day) and publish an owner-only file through `platform::private_file`; a file that does not decode or is of a later version is left alone (a later version's file is reported by each collection that finds it). The folder is checked again once the lock is held. Cache I/O runs on `spawn_blocking`. `cache/state_file.rs` holds the shared state-file operations for blocking I/O, folder privacy, locking, version-aware reads and atomic replacement. Files live in the OS cache dir (`ACTIVITY_LOG_CACHE_DIR` overrides it), never the working directory
- `core/src/diagnostics/`: in-memory diagnostic log (ring buffer) shown in the settings Logs pane; use `diagnostics::info/warn/error` instead of `eprintln!` so messages are visible in the desktop app
- `core/src/provider/connection/`: a provider kind can be configured more than once; each setup is a connection (`ConnectionId { source, name }`) with its own values, runtime, status, cache file and log scope. An adapter declares `instances()` (one or several connections) and optionally `collection_state()`/`finish_kind()` for work across its connections (Git matches emails found in all of them). Collectors stay unaware of connections: the runtime stamps `connection` on entries and scopes log lines. Each connection runs its own check → collect pipeline (`collect_planned` in `core/src/lib.rs`, which reports each connection's entries; `collect_runtimes` for the CLI, whose `RunReport` says how each connection ended), and the report is rebuilt each time one settles, so `finish_kind()` also runs provisionally (`complete: false`) while connections of its kind are pending and must then return a subset of its complete result
- A secret in `config.toml` may be `{ sealed = "v1:…" }` (`StoredValue::Sealed`, a `StoredSecret`: `Sealed(SealedValue)` or `Unreadable` with its text and `Malformed`); a string is always text, another table or a sealed field that is no secret is skipped with a warning. `ConnectionValues::get` hands on text only, `get_stored` the stored form, which `EditBase` and the collection key compare. `ProviderRuntime::inspect` opens a connection's sealed secrets with the host's `Secrets` before the check's timeout starts (its checking info says what it waits for, `Secrets::waiting_reason`), and the check and every later collection read the opened values, so no collection asks a store; a `StoreError` in an error's chain is `secretUnavailable` (`problem_of`). `Host::start` and `AppState::start` take the `Secrets` the binary built; the host probes the store once at start and each recorded check refreshes `ProvidersResponse.secretStore`
- `core/src/settings/`: `config.toml`, the connections file shared by the CLI, the API server and the desktop app (`[[gitlab]]` tables, field names without the kind prefix). It is the only list of sources: a kind it does not mention has no connections, and environment variables never configure a source. No binary reads a `.env` file into its environment: the CLI, the API server and the processes they start get only the environment they were started with, so a checkout's `.env` sets nothing (`cli/tests/settings.rs` pins it); only the one import from 0.0.7 reads one, as data. `settings/legacy_import/`: Activity Log 0.0.7's sources imported once (`docs/adr/0006-secure-secrets.md`), by the desktop before its host loads and by every CLI command but `config path` before it reads the sources, only on the default config path (`Place::for_front_end`: no `--config`, `ACTIVITY_LOG_CONFIG` or dev profile) while no `config.toml` (an empty one counts) and no `legacy-import.toml` marker are there; `v0_0_7/` is 0.0.7's own read rules, ported (`read_store_provider_config`, `list`, `bool`, `parse_config_list`, `parse_wsl_repo`; a blank value is unset), `files/` finds and reads `settings.json` (Tauri's app data folder for `com.activitylog.desktop`) and the first `.env` up from the working directory, opened once and read only if the user owns it, judged on that handle (`private_file::owned_by_user`), through `dotenvy::from_read_iter`, the first of a repeated key winning, a line that does not parse ending the file, and a setting whose line refers to a variable (`$VAR`, outside single quotes, not escaped) left out (`readsEnvironment`), since `dotenvy` fills it in from the environment; a `.env` that sets none of 0.0.7's keys counts as not found; `settings.json` wins only if it sets a key 0.0.7 read; `plan/` maps the values to connections, each through `normalize`, a refused value or a token without an address left out (`LegacySkipReason`); the edit runs under `Precondition::FileAbsent` (another writer first is `EditError::FileExists`, and the import is dropped) and writes the marker under the same lock (`edit_config_recorded`); a token needs the key first: the desktop's start asks without a dialog and waits (`Postponed`) where the store needs one, and `import_legacy_settings` (the notice's Import) asks with dialogs; the CLI asks with them. The report is a `LegacyImportReportDto` (`imported`, `postponed`, `unreadable`, `failed`, with a `message`), logged, printed by the CLI, and held by the desktop for the dashboard's one `take_legacy_import_report` (`services/legacy-import-notice.service.ts`: an `InfoNotice` with Open Settings for left-out values, a failure with Import for one refused or failed); the API only logs how to import (`legacy_import::hint`). While an import waits the CLI refuses the commands that write the settings, which would give it up, and `config skip-import` (`legacy_import::give_up`) gives it up on purpose. The CLI's tests run it with its OS folders inside their temporary folder, so none reaches the user's settings. Connection names are compared as slugs; a repeated name is numbered (`work-2`) in file order with a warning, and the next edit writes it. Read it with `load_connections`/`ConfigFile::logged_connections`, which send its warnings to the Logs pane; a table it cannot read is skipped with a warning, and edits address tables by their place in the file. Every writer goes through `settings::edit_config`: under the `config.toml.lock` lock (5 s wait, then "busy") it reads the file again, checks the writer's `Precondition` (an `EditBase` taken before any question; account fields and the table's reserved `instance` id tell a changed or re-added connection apart), applies the change, refuses a change of what a sealed secret is bound to without the secret (`ConfigEditError::BindingChanged`; bindings compared, never tags) and a new secret whose table names nothing to bind it to (`SecretUnbound`: never written as plain text; `check_save` reports both at the secret's field), gives each table it wrote an `instance` if it has none, seals every plain secret when the writer brought a `Sealer` (a writer with a new secret gets one from `Secrets::sealer` before the lock: the store its front end seals with, the key read fresh, made over a definite absence; a store that gives none is `EditError::SecretStore`, `secretStoreUnavailable` or `secretStoreRefused`), opens each value that key sealed and the edit stored anew from the bytes about to be written (one left as it was is not opened), checks the result reads, and publishes it through `private_file` unless the bytes are unchanged; sealing marks no table written. `startup_seal::seal_without_asking` seals plain secrets at the desktop's start before its host loads, without a dialog (creating a key included), waiting at most `KEY_LOOKUP` (5 s) for the key, never failing. Parse errors name the line and column, never the file's text. ### API

- `api/src/lib.rs`: Rocket routes over a `Host` (`BadConfig::Fail`: a file that does not parse stops the server with its place), its spawner (`tokio::spawn`), the startup collection and the config watcher on liftoff, `Host::shutdown` on shutdown; the activity, providers, runtime-state, collect and recheck routes first call `reload_if_changed` (events, export and logs do not; the watcher reloads for the stream), so edits from the CLI or the desktop app apply without a restart. Every error answers a `BackendError` body with the status of its kind (`status_of`); a default catcher answers one for what Rocket refuses itself (an unknown route `404`, a body that is no JSON `400` or not the route's request `422`, a panic `500`)
- `api/src/main.rs`: runtime bootstrap

Routes:

- `GET /api/activity`: `202` with a partial `ActivityLog` while a collection runs (`meta.pending` names the connections still to come), `200` with the complete log, `200` with `CollectionFailedResponse` after a failure, `503` before the first collection
- `GET /api/providers`
- `GET /api/runtime-state`: `200` with `RuntimeState`, both parts of one moment with their stamps (`docs/plans/shared-contracts.md` §5); `activity.state` is `empty` before the first collection, never `503`. A plain read; the dashboard follows `GET /api/events`
- `GET /api/events`: `200` `text/event-stream` (Rocket's `EventStream`, its comment heartbeat off) over `Host::feed` and a `Forwarder`: a `state` event (`RuntimeState`) first, then `activity` (`ActivityUpdate`) and `providers` (`ProvidersUpdate`) as each part changes, in revision order, another `state` after each authority change, and `ping` (`RuntimePing`) after `runtime::PING_INTERVAL` (15 s, generated as `RUNTIME_PING_SECONDS`) without an event, the heartbeat a browser sees; compact JSON on one `data:` line, no `id:` and no replay. A reader that lags skips values, never a part's latest. It ends when Rocket shuts down (`Shutdown`) or the host does. This is how the browser dashboard follows the host. The dev server's proxy (`dashboard/proxy.conf.mjs`) streams it as is and ends the browser's answer when the API's breaks off (the API was killed), so the dashboard's stream sees the end; `scripts/dev-proxy.test.mjs`, run by `dashboard:lint`, pins that
- `POST /api/collect`: starts the collection and answers `202` at once with its first snapshot; a collection of the same range that already runs is answered with its snapshot, one of another range is stopped. Every answer of it is a `CollectAnswer`: the log or failure as before, plus the host's own `kind` for it (`ShownActivity`: `running`, `ready`, `failed`) and `stamp` (`PartStamp`), the activity part it installed or shows
- `POST /api/connections/recheck` with a `ConnectionId`: runs that connection's startup check again (`Host::recheck`) and answers `200` with a `RecheckAnswer` (`ProvidersResponse` and the providers' `stamp`), the connection checking; `404` (`notFound`) for one the server does not have, `500` (`internal`) once it shut down (`Host::recheck` fails with `RecheckRefused`, `UnknownConnection` or `ShutDown`)
- A request body that is not `application/json` matches no route: `404` (`notFound`), Rocket's route matching, pinned by a test
- `POST /api/export`: `ExportRequest` (format, `[start, end)`, IANA `timeZone`, entries) → `200` with `ExportFile` (`fileName`, `content`), `400` with an `invalidRequest` `BackendError` for an unknown zone, a bad range or a body that is no request, `413` (`tooLarge`) above 64 MiB (this route reads its body itself; Rocket's JSON limit is 1 MiB)
- Every range (collect, export, CLI) is checked by `CollectOptions::check`: `end` after `start`, at most `CollectOptions::MAX_DAYS` (ten years); the dashboard checks a URL's range the same way, in instants, with `collectableRange` (`utils/app-url.ts`, against the generated `COLLECT_MAX_DAYS`): `DeepLinkService` drops a link's range outside that and `ActivityViewStateService.openedRange` collects none
- `GET /api/logs`, `DELETE /api/logs`

## Code Quality

Working code is not done code. A change that works but misses these rules is unfinished, and a review reports each miss as a finding, not as taste. The Rust and Angular rules below apply them to each side.

- Logic never decides anything by comparing, searching or parsing text meant for people. Tell cases apart by types: enums, discriminated unions, error kinds, status codes. Messages are only for people to read
- Make wrong states unrepresentable: one union of states instead of flags or nullable fields that must agree, and an `Option` or a variant instead of a sentinel (`""`, `-1`, `"unknown"`, a shared marker string)
- One source of truth per fact: a contract is generated from its owner (Rust), a rule lives in one place, a value is derived instead of copied. When something replaces old code, delete the old code
- Types hold across every boundary (HTTP, IPC, events, the cache, generated DTOs): no casts where narrowing works, no `any`, no error strings a caller must tell apart; untrusted input is checked where it enters
- Errors keep their kind and their cause: never swallow one, never merge different failures into one
- Tests check behaviour and fail without the fix they guard; they assert kinds and results, not wording, unless the wording is the product

## Rust Rules

- Keep shared domain and API types in `core/src/model/`, not in `api` or `cli`
- Put each model struct in its own file under the matching domain/source folder
- For Rust modules with local tests, colocate them as a folder pair: `mod.rs` plus `tests.rs` in the same directory
- Do not keep Rust code in `foo.rs` while its tests live in `foo/tests.rs`; move the implementation into `foo/mod.rs` instead
- Prefer moving reusable logic into `core` instead of duplicating behavior in `api` or `cli`
- Preserve wire compatibility for public API fields unless the task explicitly changes the contract
- The backend deals in instants: requests carry a `[start, end)` range of RFC 3339 instants and entries carry RFC 3339 timestamps. `core` and `api` never read the machine's time zone, with the exceptions below. `core` may group by local day only in an IANA time zone the request carries (the dashboard sends the browser's zone, as `ExportRequest.timeZone`; the CLI passes the terminal's), as `core::export` does; the dashboard and the CLI turn local days into instants
- Exceptions: sources that report local wall-clock time without an offset, converted where they are parsed: macOS `last`, and ICS times without a zone (floating times), which `collect/calendar` reads in the machine's zone (`local_zone()`). Floating times mean the wall clock of whoever's calendar it is, the same kind of input as `last`; passing a zone in would put the reader's zone into collections and their cache, which are shared by every reader
- Errors are typed: a failure a caller must tell apart is an enum or a kind, never a `String` (`Result<_, String>`) or a message matched by text; callers decide on the kind, never on the message, which is for people. Every error crossing the backend boundary is a `BackendError`, mapped in `core/src/backend_error/`. Tests assert kinds, not wording, except where the wording is the product (redaction, the agreed texts)
- No sentinel strings as errors or absent values (`""`, `"unknown"`, a shared `STOPPED` text): use an `Option` or a variant
- A subprocess whose output is parsed runs with `LC_ALL=C` (`last` prints its dates in the user's language otherwise)
- Use comments sparingly and only where behavior is not obvious
- Keep PowerShell and subprocess integrations parity-focused unless the task explicitly replaces them
- For OS-specific Rust implementations, gate child modules at the parent boundary with `#[cfg(target_os = "...")]`
- Name OS-specific child modules by platform (`windows`, `macos`, `linux`) and keep the dispatch in the parent module
- A parent module with OS children chooses its implementation at compile time with an `imp` alias: `#[cfg(target_os = "windows")] use self::windows as imp;` (and `macos`, `linux` where they exist; one child may serve several targets, as `platform/private_file`'s `unix` does for macOS and Linux, itself using the `macos` or `linux` child, and `platform/blocking`'s does under `cfg(unix)`), plus one `fallback` module for the targets left (`#[cfg(not(any(...)))] use self::fallback as imp;`), which answers as an unsupported system would: a connection the OS cannot have checks as `unsupported` (a WSL Git connection off Windows), and a provider whose `supported_os` leaves the target out is refused before its fallback runs. A parent whose children cover every target has no `fallback`. The parent's own functions call `imp::…`, and callers outside the parent go through them, never `imp` or a platform child. An item only one OS has (a type, a helper used by another module's code for that OS) may be re-exported at the parent for callers gated on that OS (`collect::git::has_wsl_repos`), without a fallback. A function and its no-op twin (`foo_impl`) never stand in for an OS child
- `platform` is the exception: it does not choose between implementations but is a library of OS APIs, `platform::macos` and the Windows items at `platform::`, which only code gated on the same OS calls (an OS child, or a function under `#[cfg(target_os = "...")]` such as `source_failure`'s AppleScript lookup, whose twin elsewhere finds nothing)
- Keep shared cross-platform logic in shared modules; only split into OS-specific modules when behavior is genuinely platform-specific

## Angular and TypeScript Rules

- Always maximize type safety
- Errors are typed: callers narrow on a `BackendFailure`'s or `Failure`'s `kind`, never on `message`; an ESLint `no-restricted-syntax` rule (`messageDecisions` in `eslint.config.mjs`) refuses comparing, switching on, testing or searching a `.message` (also `?.message` and `['message']`) in `dashboard/src/app`, and allows showing it; `scripts/eslint-message-rule.test.mjs`, run by `dashboard:lint`, pins both

- Hover styles go through `ui.hover` (`components/_dashboard-shared.scss`), written inside the control's rule: `@media (hover: hover)`, so a tap on a touch screen leaves no control looking hovered, not after a touch on a device that has a mouse too (`html.touch-input`, kept by `utils/touch-input.ts` until a mouse moves; the guard sits on the control itself, `:not(:root.touch-input *)`, so Angular's style scoping keeps it), and the same look at once while the control is pressed (`:active`; `$pressed: false` for a reveal or a field). A scroller sets `overscroll-behavior` beside its `overflow`, on itself, for each axis it scrolls (`auto` where it hands its scrolling on, such as a list inside a scrolling pane). `scripts/touch-styles.test.mjs`, run by `dashboard:lint`, pins the compiled mixin and refuses a raw `:hover` or a hover media query outside `ui.hover` and `ui.no-hover` (what a touch screen changes, such as the room a finger needs, or hides, such as the resting Shift tag, which it pins) and a scroller without it in every stylesheet (inline `styles` too, read with the TypeScript parser), names a stylesheet it cannot read, checks the viewport meta (`viewport-fit=cover`, pinch zoom kept), and pins the compiled `ui.field-text`. What a layout makes of the styles is checked in a browser: the layout specs (`*.layout.spec.ts`, `pnpm dashboard:test:layout`, the unit-test builder's `layout` configuration: headless Chromium through `@vitest/browser-playwright`, touch through the DevTools protocol, installed by `pnpm dashboard:browsers`) find overlapping or cut header controls at the sizes that broke, fields under 16 px on a touch screen, a notice over the collection's card, a phone slide that does not run, a button label that clips its descenders, a switch (`mat-slide-toggle`, sized and coloured once by `mat.slide-toggle-overrides` in `styles.scss`) larger than a settings switch, under 3:1 off or on in any theme or with a touch target under 44 px, and a settings pane that ends flush with its scroller's edge. The default test run leaves them out
- Touch basics are by design for every input and size, never by width: `styles.scss` (Touch) keeps the page from bouncing or reloading when pulled, drops the tap flash, and makes controls answer a tap at once, without text selection or a callout (a link that leaves the app, `target=_blank`, keeps its callout); `followTouchInput` (`utils/touch-input.ts`, started by `AppComponent`) also holds the passive `touchstart` listener that makes iOS show `:active`. The shell, the phone's bottom bar, the details, the dialogs (the confirmation's text scrolls, its actions stay), the notices and the focused skip link keep out of the screen's safe area (`env(safe-area-inset-*)`, `--dialog-max-width`, `--dialog-max-height`), which is 0 on the desktop. The text of every field people type in is at least 16 px where the pointer cannot hover (`ui.field-text($size)`), since iOS zooms the page into a field with smaller text as it takes focus and leaves it zoomed; pinch zoom stays. Notices keep clear of the bottom of the screen's other surfaces too (`--notices-bottom` in `styles.scss`): the phone's bottom bar, and the collection's pill or card, whose reach from the window's bottom `CollectionStatusComponent` sets as `--collection-status-clearance` while one shows, measured again as its size changes (`elementSize`: a font coming in rewraps it)

## Verification Rule

Always run the repo verification gate before considering a change complete:

```bash
pnpm verify
```

If `pnpm verify` cannot be run in the current environment, say so explicitly in the final handoff.

CI (`.github/workflows/`) runs the Linux check (clippy, the backend's tests, the Secret Service) on every pull request and push to main. Windows and macOS minutes cost two and ten Linux ones, so the Windows check (clippy and the tests on Windows, Credential Manager) runs on each push to main and the macOS keychain tests on a push to main that changes the secret store or the dependencies; on a pull request neither runs by itself. A change to Windows-gated code, file and path handling, the desktop crate or the secret store is not done until that workflow passed on its branch, run by hand (`gh workflow run windows.yml --ref <branch>`, or Actions › Run workflow). `cargo xwin clippy` (`pnpm win:check` in `nix develop .#windows`) compile-checks the Windows code locally. A superseded run of a pull request or a branch run by hand is cancelled, and every job has a timeout.

The macOS workflow compiles the real-store tests before creating and unlocking their temporary keychain. That keychain has no idle lock, and calls against it disable dialogs. The test execution step times out after two minutes.

`Cargo.toml` owns the workspace version. Every crate inherits it, as does Tauri, and the private JavaScript packages have no version. `pnpm release:check` checks this and the lockfile, and runs the release tests without needing Git history. Release runs by hand on `main` once Linux CI passes at its head. It uses a Cargo version newer than all tags or takes git-cliff's bump, then calls Desktop Build for that exact release commit. CI uses the repository's `GITHUB_TOKEN` to add GitHub usernames, pull request links, first-time contributors, and links comparing consecutive tags to the changelog and draft notes. Local previews run offline by default. Only after the builds pass does Release push the commit and tag and attach the installers to a draft before publishing. Desktop Build also runs by hand for a branch. The [README](README.md#releases) lists the release inputs.
